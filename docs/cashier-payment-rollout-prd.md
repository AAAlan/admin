# 收银台功能开关与支付方式灰度发布 PRD

版本：1.6 · 2026-11-03 · 状态：评审稿 + 可运行前后端 Demo

本次修订：明确两类配置归属。免密支付、卡保存与历史卡复用放在「支付渠道配置 → 子渠道配置」；支付方式开关与灰度放在「收银台模版」。两类资源各自保存、审核、发布、回滚与应急，不互相覆盖。同一模版内 CARD 的多个 PSP 共用方式规则和用户桶，但每个子渠道独立控制其功能。国家、用户 platform、名单仍为高级条件，不提供客户端条件。保留 Stripe / Adyen / Antom 公开资料调研，不新增未经核实的厂商能力声明。

交付边界：`npm run dev:full` 为海外模版和子渠道功能的真实本地后端模式，保存至 SQLite；`npm run dev` 为独立 localStorage Mock，两者不自动迁移或降级。原独立功能页已退出正式路由，仅保留未路由的历史组件及测试；`/payment/rollout-demo` 只导航到两个归属页面。渠道基础信息仍为原 Mock，功能后端使用静态子渠道注册样本，不代表真实机构开通。订单决策与支付前复核 API 已提供，但真实订单 / 用户 / PSP / SSO 未接入，缺少可信适配器时安全拒绝。不是已上线支付服务。详见 [后端接入说明](payment-rollout-backend.md)。

### v1.6 配置归属与联动验收

| 配置 | 唯一入口 | 控制颗粒度 | 共享与隔离 |
| --- | --- | --- | --- |
| PayPal 免密支付 | 支付渠道配置 → 展开 PayPal → 编辑子渠道 | 环境 × 产线 × 应用 × 渠道账户 × 子渠道 × 功能 | 引用同一子渠道的模版共用；不同账户、子渠道独立 |
| 卡保存 / 历史卡复用 | 支付渠道配置 → 编辑 CARD 子渠道 | 同上，两项功能独立 | 同一渠道下 VISA / AMEX 子渠道也不互相覆盖 |
| 支付方式展示 | 收银台模版 → 编辑 → 设置开放范围 | 环境 × 产线 × 应用 × 模版 × 业务支付方式 | 模版内同方式多渠道共享；不同模版独立 |

- 子渠道功能默认关闭；旧场景功能 cohort 不自动迁移，不把历史演示的 10% / 25% 作为新资源默认值。
- 模版方式命中只决定候选入口；选定合资格渠道后，再检查其子渠道功能发布规则、产品资格、用户授权及 token。
- 关闭免密仅降级到标准 PayPal；关闭新保存不关闭银行卡，也不自动关闭历史复用或撤销授权。
- 子渠道与模版各自使用 CAS 和独立版本 / 应急代次；功能变化也会使旧支付决策要求重新确认。
- 模版不得覆盖子渠道功能规则；功能草稿与上方子渠道基础信息分别保存，不以基础信息保存冒充功能发布。

### v1.5 后端交付与验收

- 运营保存草稿不影响线上快照；提交冻结后不可改写，独立审批才原子递增生效版本。
- 服务端按凭证限定 environment / region / appId，校验角色与 actorId，不允许自审；本地角色选择仅演示，非正式鉴权。
- 保存草稿使用 draftRevision CAS；审批检查 pendingId、基准版本和应急代次；回滚为新递增版本，不能解除应急停用。
- 同一模版内 CARD 的 Adyen / Stripe 共用 `rules.card` 与 bucket；跨模版隔离，不做 PSP 流量分配。原 v1 条目 cohort 不静默迁移，冲突渠道规则要求显式统一。
- preview 可分别试算未发布编辑内容和已发布快照，明确模拟资格；正式 decisions 只收 orderId / templateId，可信上下文由适配器获取。
- revalidate 检查原选项、TTL、版本、安全代次和最新订单事实；变化须重新确认。该接口不创建支付，不代替订单锁与幂等提交。
- SQLite 记录完整快照、版本与审计；刷新 / 重启保留。未接统一发布中心、分布式缓存、监控或生产身份系统。

## 1. 结论与设计决策

建立一套「入口与功能分层、支付资格优先、稳定用户分桶、独立审核发布、应急覆盖独立」的支付体验控制平台。

覆盖两类需求：

1. PayPal 快捷支付（业务俗称“免密”）、卡支付记住卡信息的开关与灰度。
2. 某个收银台模版内部支付方式的开关与灰度，不是全场景方式总开关，也不是 PSP 路由权重。

关键边界：

- **“免密”不是免授权或免验证。** 对外叫“PayPal 快捷支付”，仅在商户产品资格、有效用户授权及 token 满足时简化后续主动支付。PayPal 登录、风险验证、银行卡 3DS / SCA 仍由机构决定。
- **保存与使用是两个独立能力。** `card_save` 只控制新的保存邀请；`card_reuse` 控制历史 token 的展示及复用。关闭新保存不应让已保存卡突然消失。
- **支付方式入口与其子功能是两个层级。** PayPal 入口不开放时，快捷支付必须不生效；关闭快捷支付时，保留标准 PayPal 流程。银行卡新保存关闭，仍可输入新卡付款。
- **运营设置不是机构能力。** 运营“全量开启”只是允许候选，不能绕过商户开通、订单资格、用户授权及风控。
- **灰度不等于 A/B 实验。** 本期是安全发布工具，不宣称能自动判断转化提升；因果实验需要随机对照、互斥层、功效设计与固定观察窗口。
- **用户点击确认才发起主动支付。** 本期不包含离线代扣、订阅扣款授权，也不能凭“记住卡”推导 MIT 授权。

## 3. 背景、目标与不做什么

### 3.1 问题

新功能全量上线风险过大；渠道开通和页面可见状态容易混淆；记住卡和复用已有卡耦合会伤害回访体验；客户端随机数导致用户反复跳组；缺乏试算、审核、观测和紧急停止使问题难以定位和止损。

### 3.2 目标与衡量

业务目标：低风险验证快捷体验，逐步提升成功支付及回访效率，而非提高保存率而牺牲用户授权质量。

建议上线验收指标（目标值待 SRE / 支付运营确认）：

- 100% 配置发布可追溯到作用域、差异、版本、提交人与审批人。
- 比例不变、同一身份与作用域下，重复命中一致率 100%。扩量不移出原桶用户。
- 任一名单不能绕过机构未开通、已关闭父入口、授权撤销或 token 跨用户。
- 配置服务决策 p95 < 50ms（建议目标，Demo 不做性能承诺）。
- 应急覆盖传播 p99 < 10s；支付提交服务不得使用超过 10s 的应急缓存（建议目标，需架构评审）。
- 观察指标使用真实事件，不在未接数据时展示“增长 12%”等虚构结论。

### 3.3 不在本期

订阅 / 离线代扣、跨 PSP token 迁移、自动渠道路由、动态排序优化、自动实验判优、自动扩量、定时发布、全局继承与场景覆盖规则、多币种机构能力全量建模。卡片删除管理的真实机构交互作为后续独立功能；本期必须正确响应机构撤销状态。

## 4. 用户与权限

| 角色 | 允许 | 不允许 |
| --- | --- | --- |
| 配置编辑员 | 查看、编辑草稿、试算、提交、撤回自己的申请 | 发布、审批自己的申请、回滚、应急停用 |
| 独立审批员 | 查看完整 diff / 验证结果，批准 / 驳回，审核回滚 | 更改待审快照、自审、代用户签约 |
| 应急管理员 | 紧急停用 / 显式恢复指定非基础能力，查看审计 | 绕过支付资格、自动删除 token |
| 只读观察者 | 查看配置与命中原因；去标识统计待接入 | 任意写操作（后端已有 viewer 角色） |

生产服务端按 actorId 和权限校验，不只靠角色字符串；同一 actor 即使拥有多个角色，也不能审批自己提交的版本。应急路径允许先止损、后补工单，但操作原因必填。恢复应有独立权限及复核，不能因告警自行恢复。

Demo 用「运营·林晓」「审批·陈安」「应急·周宁」三个固定身份模拟职责分离，页面上明确这不是认证系统。不得将可切换身份组件用于生产权限管理。

## 5. 配置模型与信息架构

### 5.1 作用域

支付方式唯一键（v1.5 后端）：`region + environment + appId + templateId + businessMethodId`。先由可信场景匹配逻辑选中模版，再在内部筛选业务方式及合资格渠道，不叠加第二套 sceneId 规则。一个模版被多个场景引用时共用规则；不同策略使用不同模版。租户与商户鉴权仍是生产硬边界。原 Mock 保留 methodEntryId 粒度，不自动转成服务端规则。

功能开关唯一键为 `environment + region + appId + channelId + subchannelId + featureKey`。Demo 固定 `demo / overseas / saki`，渠道账户和子渠道来自当前编辑资源。它不包含 templateId / sceneId；同一子渠道被多个模版引用时共用功能规则。不同渠道账户、不同子渠道和不同功能独立。后端验证子渠道确属该渠道；未知归属安全拒绝，不按名称猜测。

模版内容与方式范围以同一个模版版本原子发布、回滚，不按行半成功生效。后端模式已实现独立状态机与 SQLite 持久化，尚未统一到 `/config-release`。旧 Mock 在 `payment_sort_configs_v1` 保存 `payment_methods[].rollout`，没有模版审批与生效版本。

Demo 部署环境固定 `demo`；现有模版 `payment_env` 的 pc / android / apple 属历史设备元数据，不用作用户 platform、目标条件或部署环境。生产环境须来自服务端可信运行上下文。

#### 5.1.1 控制维度与颗粒度

一句话定义：**方式归模版、功能归子渠道，两者均按用户稳定灰度。**

| 控制层级 | 维度 / 颗粒度 | 当前能力与边界 |
| --- | --- | --- |
| 配置归属 | 产线 × 环境 × 游戏 / 应用 × 收银台模版 | 模版 A 与 B 的规则互不修改；重命名模版不改变 ID；新建 / 复制模版获得新 ID |
| 控制对象 | 当前模版内业务支付方式 | 来自 payment_methods 的注册 businessMethodId；同一 CARD 多渠道共享范围和用户桶，渠道资格分别校验；不是 PSP 权重路由 |
| 目标人群 | 国家 / 地区、用户 platform、用户 ID 黑白名单 | 国家 / 地区与用户 platform 之间取交集；白名单仅绕过百分比。Demo 提供 US / DE / GB，以及沿用项目海外场景枚举的 apple / google / PSN / windows；不提供客户端条件 |
| 灰度分配 | 登录用户按 userId；游客普通支付入口按稳定 sessionId | 每个控制对象独立分桶，不按订单号随机分配；游客不开放本期三个保存 / 复用功能 |
| 交易安全 | 每笔订单及其实际机构、授权、token 资格 | 金额、币种、机构能力、风控、授权有效性和 token 归属是资格过滤，不是当前运营可编辑的灰度条件；命中比例不能绕过这些约束 |
| 功能归属 | 产线 × 环境 × 应用 × 渠道账户 × 子渠道 × 功能 | 共用子渠道即共用规则，不随模版复制；CARD 保存与复用独立 |
| 发布与应急 | 模版按业务方式停用；子渠道按功能停用 | 两类后端资源独立持久化审核、回滚与应急，统一发布中心尚未接入 |

v1.5 `businessMethodId` 为注册枚举，渠道条目标识为 `businessMethodId::channelId`。重排、推荐文案、同方式增加渠道不换桶。旧 Mock 的 `methodEntryId / rollout_entry_id` 逻辑保留，仅适用于其独立数据集。移除后重加同业务 ID 复用 v2 cohort；复制为新模版则为新分配单元。

#### 5.1.2 分桶颗粒度的业务表现

- 同一登录用户在同一产线、环境、应用、模版和业务方式下重复下单，分桶值保持一致；同方式的多个 PSP 不重复抽签。
- 同一用户对不同功能 / 支付方式可以命中不同结果，例如命中“新卡保存”但未命中“PayPal 快捷支付”。
- 同一用户跨模版或业务方式使用不同种子，结果可能不同（不是保证桶一定不同）；修改模版 A 不影响 B。引用同一模版的不同场景不另行分桶。
- 修改比例或发布版本不会改变分桶值；国家、用户 platform、设备、金额和币种不参与分桶种子，但可能改变目标条件或本单资格，因而最终开放结果仍可能变化。
- 游客以稳定会话为分配单位，不保证跨浏览器或跨会话一致；游客登录后的身份切换与当前订单快照策略见 6.3。
- PayPal 快捷支付的当前控制范围是**已有有效授权钱包的复用**，不包含新签约、重新授权或购买中保存钱包流程。
- 对同一子渠道功能，跨模版分桶值相同；最终体验仍受各模版方式范围约束。换子渠道则使用另一个种子，不保证具体桶值必然不同。

#### 5.1.3 父约束、迁移与未覆盖边界

模版未发布 / 停用、条目禁用 / 移除、机构未就绪、本单不合资格均阻断；白名单不能重新启用它们。关闭只隐藏当前模版中的该条目；所有条目均不可用时展示安全空态，不能偷偷恢复被灰度拦截的银行卡。生产发布前应校验目标市场至少有合资格的基础路径；本轮不把某个固定方式硬编码为所有模版的兜底。

旧 Mock 的存量无规则条目沿用原启用行为。后端新增业务方式默认关闭，新增同方式渠道继承现有业务规则；旧渠道规则冲突必须显式统一。新模版首次保存分配正式 templateId，之后才提供服务端试算；不能将旧临时桶作为发布承诺。旧模版无 templateId 时使用 canonical storage key，不能用展示序号命名。

不提供场景级继承、商品 / SKU、卡品牌、客户端版本等运营维度，不新增 PSP 比例路由。后端关闭某业务方式会隐藏该模版内该方式所有渠道；渠道停用则只排除相应渠道。命中业务方式且至少存在一个合资格渠道才可展示。其他独立决策 Demo 不随此处配置变化。

原场景级方式样本不迁移为线上规则，不把新模版种子静默用于旧功能开关，避免存量 cohort 跳组。商户 / token 归属、环境密钥隔离仍由服务端校验。

| --- | --- | --- | --- |
| `paypal_quick` | PayPal 子渠道功能 | 关闭 | 仅允许有效授权钱包快捷复用；关闭走标准 PayPal，不撤销授权 |
| `card_save` | CARD 子渠道功能 | 关闭 | 仅命中且登录的新卡流程展示保存选项；关闭后不新建 token，仍可付本单 |

### 5.3 单条规则字段

- `mode`：关闭 / 灰度 / 全量。关闭时白名单也不放行。
- `percentage`：0–100，最多两位小数，映射 10,000 个桶。仅灰度模式使用；0% 允许内部白名单，100% 仍受其他约束。
- `countries[]`、`platforms[]`：空数组为不限；同字段内 OR、不同字段 AND。国家来源需统一为机构可验证的账单 / 客户国家，不能信任客户端自报。
- `platforms[]` 对应 `profile.platform`，只接受项目海外枚举 `apple / google / PSN / windows`（复用 `PLATFORM_OPTIONS_OVERSEAS`）；多选取并集。用户 platform 由生产可信用户 / 会话上下文提供，不按当前浏览器、操作系统或支付设备推导；Demo 手选仅用于试算，未接入真实用户平台数据。
- `profile.device` 仅在预览“高级边界测试 → 支付设备环境（资格样本）”中保留，独立验证 Apple Pay 等设备硬资格，不是灰度条件。例如 google 用户在 iOS 设备访问 Web，用户 platform 仍是 google；apple 用户用不支持的钱包环境也不能使用 Apple Pay。
- 原 `devices[]` 条件已移除。带旧字段的导入 / 待审 / 回滚快照会校验失败，不将 Web / iOS / Android 自动映射成用户 platform，也不静默丢弃旧限制。旧场景功能规则不迁移至新子渠道；生产若已有旧规则须另行显式迁移及审核。
- `allow` / `deny`：用户 ID 集合，去重、去空白，单名单最多 100 个。逗号、中文逗号、空白、分号分隔。冲突时 deny 优先。游客不匹配账号名单。
- 分桶种子由作用域和 flagKey 固定派生，不允许运营随意更换；重置 cohort 属新实验 / 新配置键，需单独评审。
- 条件仅收窄开放范围，不产生支付授权。

生产扩展字段：owner、expiry/reviewAt、reason、ticket、schemaVersion、baseVersion、revision、configHash。名单在传输和存储时做权限保护，不在一般埋点输出明文。

### 5.4 页面结构

`/payment/rollout-demo` 仅保留两个导航入口，不编辑任何规则。功能日常流程：**支付渠道配置 → 展开渠道 → 编辑子渠道 → 功能开关与灰度 → 保存功能草稿 → 独立审核发布**。方式日常流程：**全局收银台模版 → 编辑具体模版 → 对应方式设置开放范围 → 应用到当前模版 → 保存模版草稿 → 独立审核发布**。

| 位置 | 简化后的交互 | 保留的边界 |
| --- | --- | --- |
| 子渠道功能 | PayPal 子渠道显示免密一项；CARD 子渠道显示卡保存与历史卡复用两项 | 不支持的子渠道不展示功能区；三项功能各自独立，功能保存不触发基础信息保存 |
| 支付方式灰度 | 现有模版编辑器每条方式行展示范围与「设置开放范围」，替换原启用 switch，不增加第二个开关；查看模版时仅查看 | 不提供跨模版批量总开关；保留排序、推荐、添加 / 移除；人群条件有摘要提示 |
| 开放范围弹窗 | 唯一三态控件「关闭 / 灰度 / 全量」；仅灰度显示比例输入及常用快捷值；保存后更新草稿 | 关闭和全量保留但不使用已填有效比例；未完成 / 非法比例在离开灰度时恢复为上次保存值，避免隐藏字段阻塞保存；模式切换不清空高级条件 |
| 指定用户验证 | 弹窗内快捷入口，设置灰度 0%、展开并聚焦白名单 | 仍是原三态模型；不自动添加当前用户，不清除国家、用户 platform 及黑名单。0% 无名单为“暂不开放”，有名单为“仅指定用户 · 白名单 N 人”；N 是去重名单数，不是实际合资格人数 |
| 高级设置 | 国家、用户 platform、黑白名单默认折叠；已设置时有提示，列表展示条件摘要 | 全量指条件内全量，仍受黑名单、资格和应急限制；收起不代表条件失效 |
| 模版方式效果试算 | 默认折叠，按需展开本模版全部条目；当前条目使用未保存编辑值，可改用户 ID、国家、用户 platform 与机构 / 交易资格样本 | 明确为「发布后假设试算」，不是当前线上状态；关闭只舍弃弹窗编辑，应用后仍需保存模版；无可用条目显示空态 |
| 功能效果试算 | 子渠道功能区内默认折叠，当前编辑 / 已发布来源可切换；首次保存后可服务端试算 | 父方式、资格和授权是显式样本；不自动选择或发起支付，参数变化使旧结果失效 |
| 发布记录与回滚 | 当前资源底部折叠「历史版本、回滚与应急」 | 审批身份才能回滚；回滚生成新版本，不清除应急覆盖；无跨资源总停用 |
| 演示身份 | 发布区内切换运营、独立审批、应急、只读 | 仅本地演示；非编辑身份只读；待审冻结编辑，独立审批后生效 |
| 安全与状态 | 发布区展示草稿修订、生效版本、应急代次、待审和差异 | 法定同意、token 和风控校验不变；功能变化不误报模版版本变化 |

提交发布仍需查看差异、填写原因、提交审核，再由独立审批身份审核发布。预览为推荐但非强制步骤；无未发布变更或已有待审核快照时不可重复提交。基础配置只读时不展示保存按钮。

发布工作流采用「保存草稿 → 提交审核 → 审核发布」。模版和子渠道复用同一后端状态机，使用 SQLite 不同资源命名空间保存快照，不是两套可互相覆盖的规则来源。尚未接入 `/config-release` 共享草稿池。Mock 子渠道仅保存本机规则，不模拟正式审批成功。

模版保存语义：应用只改表单；取消弹窗不改变规则；重置恢复已保存快照；关闭未保存表单不写存储；只读不应用/保存；服务错误不报成功、不降级 Mock。后端草稿与生效版本严格区分，发布与回滚见 §7。

简化验收：方式在所属模版内配置；无第二个布尔开关；非灰度不显示比例；高级条件默认收起；查看态不可修改；移动端弹窗可滚动；功能历史卡复用保持独立。

### 5.5 机构准入与开放规则分层（v1.3）

| 层 | 谁负责 / 粒度 | 与本次配置的关系 |
| --- | --- | --- |
| 机构能力 | 支付接入系统；生产按 environment × merchantAccount × provider × method / product | 来自合同、机构查询 / 通知及账户配置，只读输入；不是运营可发布字段 |
| 运营开放 | 方式按 environment × region × app × template × businessMethodId；功能按 environment × region × app × channel × subchannel × featureKey | 三态、人群条件、名单与用户桶；生产对接统一审批发布 |
| 单笔资格 | 支付服务；用户 / 订单 / 设备 / token / 风控 | 每次展示和支付提交校验；前两层通过不代表本单一定能支付 |

后端 `capabilityReader` 与 `featureCapabilityReader` 为独立可信能力来源，**不进入版本配置**；子渠道归属由 `subchannelReader` 验证。演示注册仅允许明确列出的海外样本账户及子渠道，其他资源不猜测资格。生产须分别映射机构的方式开通与功能产品资格，不能因普通 PayPal / 卡已开通就推导保存或快捷产品也获批。

子功能依赖父方式及所选渠道 / 子渠道可用：父方式不可用阻断子功能；仅子功能未就绪不隐藏普通方式或兄弟功能。缺失、不识别或未知状态一律视为未就绪，白名单和“全量”不可绕过。基础银行卡也不能绕过真实机构故障，不能保证永远有可付方式。

功能试算可取消“本单 / 机构资格”与“有效授权及 token”样本，验证阻断；这些不是正式开通按钮，且不能绕过后端独立产品准入。渠道基础信息仍为 Mock，其增删 / 启停不会自动修改服务端注册适配器。正式接入必须统一可信主数据，不能依赖浏览器的 Mock 状态。

## 6. 决策规则

### 6.1 优先级与依赖

后端模版方式：先校验 schema / scope / 注册业务 ID 与唯一渠道条目，再判断模版已发布且启用 → 业务方式应急 → 业务方式关闭 → 黑名单 → 启用且机构/本单合资格渠道 → 订单硬约束与稳定身份 → 国家与用户 platform → 白名单 → 全量或稳定百分比。至少一条合资格渠道才展示该业务方式；未知资格 fail closed。管理试算用手选样本，不是支付承诺；运行时禁止客户端传 profile/资格。

子渠道功能决策高到低：

`未发布 > 应急停用 > mode=off > 父方式 / 渠道 / 子渠道不可用 > 黑名单 > 可信登录 > 产品 / 本单 / 风控资格 > 有效授权与 token（复用功能） > 国家与用户 platform > 白名单 > 全量或稳定百分比`

父方式先决策，功能后决策。功能控制的是“能否提供该体验”，而不是“用户是否已经选择”。举例：card_save 命中但用户选历史卡，不能为历史卡再次申请新保存。

白名单只能绕过百分比，不能绕过目标条件、关闭、硬资格或应急。名单同时命中时黑名单优先。目标人群外不进入实验，不得算作控制组曝光。多个功能可独立命中；不要求三个功能共用 cohort。

### 6.2 稳定分桶

本 Demo 约定可跨语言复现的算法：

```text
identity = 已登录 ? "user:" + canonicalUserId : "session:" + stableSessionId
// 支付方式（新增独立命名空间，不更改原功能 cohort）
seed = JSON.stringify(["template-business-v2", environment, region, appId, templateId, businessMethodId, identity])
// 原本机 Mock 保留 ["template-method-v1", region, environment, appId, templateId, methodEntryId, identity]
// 子渠道功能：仅已登录 user 身份，不含模版、订单、比例或版本
featureSeed = JSON.stringify(["subchannel-feature-v1", environment, region, appId, channelId, subchannelId, featureKey, "user:" + canonicalUserId])
// 历史未路由功能组件的 [environment, gameId, sceneId, flagKey, identity] 不迁移
bytes = UTF8(seed)
hash = FNV1a32(bytes)  // offset 2166136261，逐字节 xor 后乘 16777619，保留 uint32
bucket = hash % 10000
threshold = round(percentage * 100)
hit = bucket < threshold
```

JSON 数组避免分隔符歧义。必须固定 UTF-8、大小写、ID canonicalization 和整数溢出语义，增加跨语言黄金向量测试。不能用 `Math.random()`、时间、订单号、配置版本或百分比作为 seed。FNV 不是密码学算法，不能用于鉴权；生产可改为服务端 HMAC 分桶防猜测，但那是显式迁移，必须冻结老 cohort 或采用新配置键，不能静默替换算法。

子渠道黄金向量：`demo / overseas / saki / paypal_merchant_paypal_001 / 5 / paypal_quick` 下 `pilot_user → 6263`、`测试用户_42 → 9226`。见 `tests/subchannel-rollout.mjs`，另覆盖跨模版同桶、比例单调扩量与多账户隔离。历史未路由功能组件的黄金向量仅用于旧算法回归，不是本次 cohort。

1%→5% 扩量，旧桶仍在新阈值内；缩量、变更国家 / 用户 platform 条件、授权撤销或名单变动可能移出用户，发布前提示。灰度比例作用于目标条件内账号或会话，不等同总 DAU / 订单曝光比例。10% 在小样本下不保证恰好 10%。

### 6.3 游客与会话

- 普通支付方式：游客可按服务端签发的稳定 sessionId 分桶，不依赖临时随机数。
- 保存 / 复用：本期要求已登录，防止共享设备泄露钱包或卡片。不能以 cookie 直接识别另一账号的 token。
- 游客登录后身份变化：下个收银台会话使用用户分桶；当前订单先冻结已有展示，不突然替换选择。Demo 为实时试算器，修改条件即时展示结果且清除已失效选项。

### 6.4 资格与 token

支付方式需要机构账户已开通，且支持本订单的环境、币种、国家、实付金额、设备、交易类型和账户状态；金额使用折扣及税费后的最终值，服务端使用货币最小单位。

快捷复用还须 token 有效、授权未撤销、user / merchant / environment 一致、授权用途包含本次主动复用。显示卡品牌、末四位等最小元数据即可；不存 PAN / CVC，不日志记录 token 密文或 client secret。卡片字段应由支付机构安全组件收集。

机构要求 challenge → 进入机构验证，不把命中结果标成付款成功。用户拒绝或保存失败 → 本单结果与存储结果分开处理，不能仅因保存失败重扣支付。

### 6.5 保存选择和 PayPal 授权

- 只在命中 `card_save`、已登录且选用新卡时显示保存选项；默认 false，每次会话或条件改变不得保留陈旧勾选。
- 记录 `consentVersion / purpose / timestamp / userId / merchantAccount / channel / locale`；若包括未来离线扣款，必须另外设计明示授权，本期不做。
- `card_reuse` 开启且历史 token 有效时，可展示已有卡；允许显式切到“使用新卡”，不能在资格变化后自动改选支付方式。
- PayPal 未授权 / 失效：标准 PayPal 仍可支付，但本产品不自绘“同意即保存钱包”路径。根据当前 PayPal 文档警示，签约 / 保存必须采用商户被批准的最新官方流程；上线前由支付接入与法务确认。
- 平台停用不等于用户撤销授权。用户撤销应通过账户管理 / 机构撤销接口及回调使相关 token 立即不可复用；已有合法订阅另按合同处理，不能被本期开关误停。

## 7. 发布、应急与回滚

本节区分已实现的本地状态机与生产要求。v1.6 后端模版、子渠道功能均已实现保存、提审、独立审批、回滚、应急与审计；Mock 只有 localStorage。后端草稿保存不是审核发布，两类资源互不发布。

生产模版发布流程：编辑某模版及其方式范围 → 保存模版草稿 → 展示本模版差异 / 受影响场景 → 独立审批 → CAS 校验模版 baseVersion → 原子发布。服务端在选中模版后先过滤被关闭 / 未命中 / 不合资格的条目，再交给排序和支付会话创建；支付提交重查同一模版版本、条目存在性与应急状态，失效时要求用户重新确认，不静默切换到别的方式。灰度关闭不得打断已提交的原笔支付或跳过查单。

回滚必须恢复同一模版的内容与规则快照为新递增版本，其他模版保持不变；条目应急覆盖独立于版本，不随回滚清除。并发修改、机构状态变更、目标范围扩大仍须校验。模版 ID / 条目 ID 不随版本变更，比例变化保留稳定桶；拷贝为新模版则是新分配单元。

子渠道发布只改变该渠道账户 / 子渠道内功能快照，不变更任何模版；引用它的模版可受到体验变化影响。决策记录包含功能版本 / 应急代次及结果的 `featureSnapshot` 哈希；即使模版版本不变，功能变化也必须在支付前复核时使旧决策失效。没有可信子渠道绑定时不开放任何功能，但合资格标准支付仍可保留。

### 7.1 状态机

`草稿 → 待审核 → 已发布`；待审核可驳回 / 撤回回到可编辑草稿。审核使用提交时的不可变快照，不接受审核人偷偷改内容；变更后重新提交。Demo 同时最多一份待审。

提交与发布两次校验 schema、比例范围、基础兜底、scope、baseVersion。并发发布以 CAS / 乐观锁拒绝过期版本。审批者不能是提交者。大范围关闭、扩大名单、缩量或跨 50% 建议提升审核级别（生产策略待定）。

v1.3 发布前检查：显示机构准入结果、基础规则保留与授权边界。允许未就绪对象保存规划草稿；**提交、审批、回滚都检查当前机构状态，不能新增 / 扩大未就绪对象的开放范围**。审核不复用提交时的机构状态；待审期间若变成未知，阻止发布且保留待审快照，可恢复可信状态后重试，或驳回 / 撤回重做。

为避免故障时无法止损，未变更对象不阻塞其他发布；关闭、0% 无白名单及可证明的范围子集允许提交。子集判定采用保守规则：比例不升高、国家 / 用户 platform 不放宽、原黑名单不移除、没有新增超出原覆盖的白名单。混合“降比例 + 加白名单”可能扩展用户集合，不能只凭比例下降放行。无法证明收窄时按扩量处理；运行时始终校验全部当前准入，不因历史规则未变而放行。

生产要求记录 actor、时间、scope、原因、ticket、diff、配置 hash、操作前后版本和请求 ID，并提供防篡改、脱敏、保留策略。后端两类资源已有持久化 actor / scope / 原因 / 请求 ID / 版本 / hash 与完整历史快照，尚无 ticket 对接、防篡改审计平台及留存清理。

### 7.2 应急停用

独立覆盖层 `kills[key]` 高于任一已发布版本，独立审计。模版内按业务方式、子渠道内按功能精确停用，不提供跨资源总停用。停用免密不隐藏标准 PayPal，停用某模版方式不修改子渠道功能规则；不应因单个钱包故障盲目停用全部方式。

停用后：

- 新会话不展示对应入口或新功能；已打开但未提交的会话，在点击支付时重新检查并提示重新选择，不静默切换。
- 已发起 / 待结果支付继续查原笔，不创建替代扣款。应急开关不擅自取消机构支付，也不退款。
- 不删除 token、不自动撤销用户授权；这些是不同业务命令。
- 所有待审核快照作废，须基于最新安全状态重新提审。
- 发布 / 回滚不解除停用，必须走“显式恢复”路径并记录原因。恢复也会使待审核快照失效。

### 7.3 回滚

回滚把历史完整规则复制为新递增版本，而不是把当前版本号倒退；保留所有过去记录。应急覆盖仍有效。回滚按 7.1 再检验当前准入，不能重新开放已经未就绪的能力；只关闭 / 收窄可继续。Demo 由审批员选择历史版本、看 diff、填原因后回滚；不恢复机构状态或 token。应急恢复仅解除应急覆盖，机构未就绪时仍不可用。

### 7.4 缓存与异常

- 生产为每单冻结配置展示快照，携带 revision、decisionId、expiry，但快照不能替代支付提交资格检查。
- 配置服务不可用：使用最近已知良好且未过期配置；无可信配置则新功能默认关闭，新支付方式隐藏；基础支付仍需独立确认机构可用，不能凭缓存“全量”绕过风控。
- 应急状态不可确认 / 缓存过期：非基础能力 fail closed；基础方式按独立安全路径决定。不能先扣款再补规则。
- 原笔支付 processing / unknown：先查单；不根据灰度变化换支付方式重扣。幂等键、providerReference、订单状态机共同保护。
- 发布传播期间按会话快照提供一致体验，服务端执行最新安全约束；监测节点版本收敛，未收敛不可继续扩量。

## 8. 埋点、监控与发布门槛（生产要求）

### 8.1 事件及分母

| 事件 | 触发 | 必要属性 |
| --- | --- | --- |
| rollout_decided | 服务端完成资格 / 分桶 | decisionId、scope、revision、flagKey、bucket、reasonCode、eligible、variant |
| payment_method_exposed | 入口实际可见 | decisionId、methodKey、sessionId、position、visibleAt |
| feature_exposed | 保存选择 / 快捷按钮实际展示 | decisionId、featureKey、variant，不能用“命中”替代曝光 |
| card_save_consent / token_created | 用户同意 / 机构确认成功，分别记事件 | 脱敏用户、consentVersion、purpose、provider、关联 ID |
| payment_submitted / payment_result | 主动提交 / webhook 最终结果 | orderId、attemptId、methodKey、providerReference、challenge、finalStatus |
| rollout_changed | 发布 / 回滚 / 停用 / 恢复 | actorId、beforeVersion、afterVersion、diffHash、reason、ticket |

去重规则：曝光按 session + object + revision 去重；支付按 orderId / attemptId 与机构最终状态对齐；token 事件按 provider eventId 幂等。前端成功页不能作为最终支付成功的唯一来源。

核心指标：支付完成率 = 唯一成功订单 / 唯一收银台有效会话；支付成功率 = 机构最终成功 attempt / 已提交 attempt；快捷钱包使用率、保存同意率、token 成功创建率分别使用对应真实曝光 / 同意分母。需同时看整体转化，防止方式占比迁移被误当提升。

### 8.2 建议观察门槛

建议起点，非厂商标准 / 既有数据：

- 内部白名单验证后 1%→5%→25%→50%→100%，每步人工审批，样本和时长以统计功效与风险预算评审为准。
- 每阶段至少观察一个完整业务周期；低样本不自动放量。拒付 / 争议有滞后，应保留长窗口。
- 若支付成功率相对下降 > 5%，或配置 / SDK 错误 > 1%，且每组最终 attempt ≥ 200，触发停止扩量与人工排查；紧急事件不受样本门槛限制。
- 严重授权越权、跨用户 token、重复扣款、数据泄露：单例即停，无需等待统计显著性。
- 同时分国家、设备、方式和新老用户观察，控制节假日、商品和营销活动混杂；不能仅将“命中组 vs 未命中组”称为严格随机实验结论。

Demo 不接这些事件、指标或自动门槛，明确显示无真实统计。后续接入后再做监控面板，避免空图表伪数据。

## 9. 技术接口建议

模版方式接口建议复用既有模版资源：`GET /v1/cashier-templates/:templateId` 获取模版版本、条目和范围；`POST .../:templateId/drafts` 保存整包草稿（baseVersion）；`POST .../:templateId/releases` 审批后原子发布；`POST .../:templateId/rollback` 回滚整包。决策上下文必须带服务端选中的 templateId / revision，条目返回 methodEntryId 与 reasonCode，不能由浏览器自报模版或灰度结果作为支付授权。

功能接口应归属子渠道资源，不再提供可编辑的场景级功能总表。本地已实现 `/api/rollout/channels/:channelId/subchannels/:subId/features` 及其 draft / submit / approve / reject / withdraw / rollback / kill / resume / preview / versions / audit 子路径。发布状态机与模版复用，存储命名空间隔离，详见后端接入说明。

本节 `/v1` 接口为生产设计建议，其中 `featureResource` 表示 `/v1/payment-channels/:channelId/subchannels/:subId/features`。已实现的 `/api/rollout` 本地接口与其不是同一已上线网关，具体请求、权限、启动方法以 [后端接入说明](payment-rollout-backend.md) 为准。

```text
GET  {featureResource}                         # 子渠道配置、版本及安全覆盖
GET  /v1/payment-capabilities?scope=...           # 独立只读机构能力及可信时效，不属于配置版本
POST {featureResource}/preview                 # 显式标记模拟，不作为支付授权
POST {featureResource}/reviews                 # baseRevision + config + reason
POST {featureResource}/reviews/:id/approve      # 鉴权、非本人、CAS、schema 二次校验
POST {featureResource}/reviews/:id/reject
POST {featureResource}/rollback                # targetRevision + baseRevision + reason
POST {featureResource}/emergency-stop          # 精确 featureKeys，不传模糊通配符
POST {featureResource}/resume                  # 显式恢复，独立权限
POST /v1/cashier/decisions                       # 从服务端用户 / 订单 / provider 构造上下文
POST /v1/payments                               # decisionId + methodKey + orderId + idempotencyKey
```

决策响应建议包括 scope、revision、emergencyEpoch、decisionId、expiresAt、allowedMethods、featureActions、reasonCodes；不要返回敏感 token 全文或把 allow-list 当权限凭证。前端请求不得信任传入的 userId、token 所有权、国家或实付金额；从登录态和订单服务取值。支付提交重查父入口、应急、授权、token 和原笔状态。

Stripe 适配：新支付优先 Checkout Sessions + Payment Element；独立保存用 SetupIntent；不走 Charges / Sources；方式选择优先动态支付方式、配置 ID 或排除规则，不硬编码 `payment_method_types` 限制正常线上支付。Adyen 适配按所用 Sessions / Advanced flow 使用 consent 与 token 参数，并消费 token 生命周期回调。PayPal 按账户获批能力和当前官方指南单独确认，不直接沿用其他钱包参数。

Antom 适配建议：服务端计算 `allowedMethods` 后，经当前官方 `createPaymentSession (One-time Payments)` 指定方式能力映射成机构支持的参数（具体字段按所选产品 / 版本沙箱核实）；前端原样交付 `paymentSessionData` 给 Payment Element，不改写它实现灰度。即使机构支持单方式跳过列表，也不自动发起支付；必须保留用户主动确认与额外验证。开通状态通过可信适配层同步，含 source、observedAt、expiresAt 和 providerReference；过期状态转未知，不沿用“已就绪”。客户端无法伪造或更新生产准入。订单创建、幂等、通知验签和查单须在正式接入阶段实现，Demo 未模拟 API 成功。

## 10. 验收用例

模版方式与子渠道功能验收：

- A / B 两个模版包含同名方式，修改 A 的比例 / 条件，B 不变；后端同模版同业务方式的两个渠道共用规则和用户桶，资格独立（旧 Mock 仍按条目）。
- 改顺序、推荐文案、模版名称、配置版本不换桶；比例扩量包含旧命中组；用户 platform 是筛选条件而不是分桶或客户端维度。
- 存量无规则条目兼容原启用状态；保存后再次打开保持规则；取消、重置和只读不写存储；保存失败不报成功。
- 未发布 / 停用模版、条目禁用 / 关闭 / 移除、未知机构资格、黑名单均不能由白名单绕过；缺失 ID、重复条目 ID、旧 devices 条件或非法比例 fail closed。
- 空可用集合展示空态，不自动恢复其他方式；A 的发布 / 回滚 / 应急不得变更 B（后端已支持，真实支付集成仍待验收）。
- 两个模版引用同一子渠道，共用功能规则与功能桶，但各自按模版规则决定方式是否展示。
- 不同账户、不同子渠道的免密 / 保存规则独立；CARD 保存与历史复用独立，修改其一不改变另一项。
- 子渠道归属从可信注册读取；runtime 缺少可信绑定不猜测，不开放快捷 / 保存功能。
- 子渠道功能单独发布、应急变化使旧 decision 失效，不必伪造模版版本递增。

| 场景 | 预期 |
| --- | --- |
| 三项功能各自关闭 | PayPal 标准流程保留；保存选项消失；历史卡复用按独立规则判断 |
| 关闭 PayPal 父入口 | 标准及快捷同时不可用，即使用户在快捷白名单 |
| 0% + 白名单 | 目标条件内、满足硬资格用户可用；其他用户不可用 |
| 点击仅指定用户验证 | 三态仍为灰度、比例为 0，展开并聚焦白名单；保留已有高级条件；空名单不开放 |
| Klarna 开通处理中但保存全量草稿 | 草稿可保存；合资格德国订单仍不展示；提交发布检查阻断 |
| 仅卡保存产品未开通 | 新保存选项不可见；普通银行卡和合资格历史卡复用不受误伤 |
| 提交后机构从已就绪变为未知 | 审批再次检查并阻止新增 / 扩量，版本不变；快照可撤回 / 驳回 |
| 未就绪时关闭 / 收窄；无关项未变 | 允许发布止损；降比例同时新增白名单不能当成纯收窄 |
| 回滚将重新开放未就绪能力 | 阻止回滚；不会改变机构状态或解除应急 |
| 应急恢复但机构仍未开通 | 仅清除应急覆盖，运行时继续阻断；不触发机构开通 |
| 同 ID 同时在黑白名单 | 黑名单胜出 |
| 白名单 + mode=off / 非目标地区 / 未开通机构 | 全部不可绕过 |
| 同一 userId 连续试算及版本更新 | 相同桶；变更比例只改变阈值，不重新分桶 |
| 同一用户在同一作用域重复下单 | 同一控制对象分桶一致，不按订单号重新抽签；最终可用性仍需逐单校验 |
| 高级设置的用户 platform | 选项仅 apple / google / PSN / windows；不选为全部，多选取并集，与国家取交集；没有客户端条件 |
| 同用户 platform、切换支付设备环境 | 用户 platform 筛选结果不随设备变化；Apple Pay 等硬资格仍独立校验 |
| 白名单用户不在目标 platform / 旧 devices 字段 | 前者返回 PLATFORM_MISS，白名单不可绕过；后者拒绝配置，不自动映射或放宽 |
| 修改国家 / 用户 platform / 设备 / 金额 / 币种 | 分桶值不变，但目标条件或本单资格可使最终开放结果变化 |
| 同一用户比较两个不同控制对象 | 分别计算分桶，不要求共同命中，也不复用另一功能的放行结果 |
| 10% 扩至 25% | 全部原 10% 桶仍命中，新增用户来自新增范围 |
| 游客 / 缺少身份 | 游客普通支付按 session 分桶，三个保存 / 复用功能不可用；缺稳定身份时报错 |
| 授权撤销 / token 跨账号 / token 失效 | 不复用；标准入口不被误隐藏；不会自动创建新 token |
| 选择历史卡 vs 新卡 | 只有新卡流程显示保存选择，默认未勾选 |
| 保存选项未勾选 | 可模拟本单支付，不创建 token |
| 机构要求验证 / 风控阻断 | 前者提示需验证而不报成功，后者本单禁止；名单不绕过 |
| 草稿未发布 | 生效配置保持不变，草稿测试显式标注 |
| 自审 / 过期版本 / 非法比例 | 服务端拒绝，原配置不变 |
| 应急停用后回滚 | 当前资源应急继续有效，待审核作废；其他资源不受误伤 |
| 应急恢复 | 仅显式恢复后按当前已发布规则判断，不能由回滚恢复 |
| 已发起 / 结果未知支付 | 禁止切换重扣，提示查原笔 |
| 无任何适用方式 | 明确空态，禁止付款，不盲目兜底机构不支持的方式 |
| 刷新 Demo | 后端两类资源从 SQLite 读取；Mock 两类规则从独立本机存储读取，均保留；两者不互相发布 |

## 11. Demo 交付范围与运行

访问 `/payment/rollout-demo`；左侧「收银台（海外）→ 功能开关与灰度发布」。

```bash
npm run dev:full
npm run test:rollout-api
npm run test:subchannel-rollout
node tests/subchannel-rollout-flow.mjs
npm run build
```

推荐演示：

1. 从导航页前往「支付渠道配置」，展开 PayPal，编辑子渠道。在功能区选择灰度 0%，高级设置填写白名单 `pilot_user`，选择用户 platform，保存功能草稿。
2. 展开「功能效果试算」，验证草稿白名单命中；取消有效授权样本后不提供免密；未发布来源不能冒充线上结果。
3. 填原因提交审核，切独立审批人，检查差异并发布；已发布来源试算与刷新持久化保持一致。
4. 编辑 CARD 子渠道，分别设置卡保存与历史复用；验证另一个子渠道不变，关闭新保存不自动关闭历史复用。
5. 前往「收银台模版」，在具体模版的支付方式行设置开放范围，应用并保存服务端草稿、审核发布。修改 A 模版不改变 B；发布模版不改子渠道功能。
6. 在当前资源「历史版本、回滚与应急」中停用 / 回滚 / 显式恢复，验证资源隔离。接口测试另外覆盖待审期间资格变化、旧 decision 失效与运行时可信子渠道绑定；Demo 不发起真实支付。

已实现：后端模版业务方式及子渠道功能三态、用户 platform / 国家 / 名单、稳定桶、服务端试算、SQLite 草稿 / 生效快照 / 审计、CAS 并发保护、独立审核 / 驳回 / 撤回、准入复验、回滚与应急覆盖、可信订单决策与资格复核接口。原 Mock 为独立存储，历史未路由功能组件仅作算法 / UI 回归参考。

未实现：正式 SSO、真实机构 / 用户 / 订单适配器、SDK / token / 支付创建 / 查单、分布式传播 / 缓存 / 高可用、支付原子提交锁、真实埋点 / 告警、定时 / 自动发布。单节点持久化与 bearer 凭证已实现，不等于生产安全及可靠性验收。

作用域与颗粒度限制：后端覆盖海外模版支付方式及注册的子渠道功能；国内模版、场景和渠道基础信息仍为 Mock。子渠道注册、产品资格与 runtime 绑定必须由可信适配器提供，演示静态样本不与 Mock 增删 / 启停自动同步。可信选模版、收银台前台实际调用决策、支付锁与幂等、商户独立运营、商品维度、全局继承与共享发布中心待接入。

## 12. 上线前必须确认的决策

- 支付接入负责人：PayPal 实际获批产品、是否支持目标市场快捷体验、当前指南下推荐签约入口及验证降级路径。
- Antom 接入负责人：目标商户、市场和产品的开通流程、状态来源与时效、Payment Element 指定方式参数及授权 / token 生命周期；若要精确复刻 Dashboard，补充脱敏私有后台证据。
- 法务 / 隐私：各市场保存及复用的授权文案、目的、期限、撤销途径与数据留存。
- 业务负责人：配置是否按游戏 / 场景 / 商户更细分，兜底方式集合及关闭行为。
- SRE / 架构：应急传播和缓存 TTL、幂等 / 查单依赖、最终性能和可用性 SLA。
- 风控 / 数据：准入规则、风险预算、统计窗口、阶段门槛和扩量审批。
- 安全：服务端用户 / token 绑定、角色隔离、双人审核、审计防篡改与名单脱敏。

以上阻塞**生产上线**，不阻塞本地交互验证。建议先评审术语与能力边界，再与真实机构适配层对齐，最后进入沙箱联调和生产小流量。

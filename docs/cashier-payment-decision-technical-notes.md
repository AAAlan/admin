## 二、决策输入与配置建议

### 2.1 决策输入

- 后端可信事实：游戏/应用、业务线、生产或测试环境、支付场景、订单金额与币种、交易类型、商户账户授权及方式能力范围。金额使用最小货币单位。
- 设备信息：平台、收银台形态、设备环境、模拟器状态、钱包/浏览器/SDK 能力。模拟器状态与生产/测试环境分别管理。
- 交易地区：使用业务验证的付款国家；IP 和语言只作辅助，不能单独作为合规依据。缺失必要信息时先补充，不猜测资格。
- 偏好信息：已登录用户、获准使用的成功历史及其作用域，仅根据成功支付记录推断。游客不跨设备识别，不使用指纹关联账户。
- 运行状态：方式、渠道及商户账户开关、健康状态、状态有效期。

资格涉及的必要能力未确认时不可选。健康信息未知时按预先批准的有效期和安全降级策略处理，不能因排序服务降级而放宽资格。

### 2.2 关键对象与字段

| 对象 | 建议字段与约束 |
| --- | --- |
| 场景规则 | `rule_id`、作用域、`priority`、结构化条件、`template_id`、生效时间、状态；数字越小优先级越高 |
| 场景模板关联 | `template_id`、是否默认、`fallback_order`、绑定的发布版本 |
| 模板 | 币种、兼容范围、`sort_mode`、`default_selection_policy`、版本；首期条件不提供任意脚本 |
| 展示方式 | `display_method_key`、`sort_order`、启停、推荐文案、多语言、执行路径 |
| 执行路径 | PSP、商户账户、子渠道、能力约束、授权范围、状态；密钥不进入普通配置或日志 |
| 偏好策略 | `preference_source=recent_success/frequent_success`、有效窗口、半衰期、最低成功证据、历史作用域 |
| 数据策略 | `ranking_policy_id/version`、分群/特征版本、有效期、数据覆盖与不确定性门槛、更新门槛 |
| 实验与降级 | 实验 ID、流量、分组单位、对照策略、评分响应预算、回滚规则、备用策略 |

排序模式为 `fixed / preference / data_driven`。模板提供默认值；场景仅通过明确的覆盖项调整，界面同时显示配置来源和最终生效值。

初期偏好窗口、统计阈值等由平台级策略统一管理，不全部开放给运营自由修改。默认选中与排序分别配置；显示第一项不自动选中。

## 三、模板、资格与排序执行

### 3.1 模板匹配

候选必须同时满足：同应用/业务线/生产或测试环境、当前场景授权关联、已发布、时间有效、币种及支付形态兼容。

依次尝试命中规则模板、场景默认模板、显式备用模板。规则按优先级升序，备用按备用序号升序；每一候选都执行资格检查，无可支付方式则记为 `TEMPLATE_EMPTY` 并继续。选定后不混合其它模板方式。

发布时阻止可能同时命中的同优先级规则。历史脏数据仍冲突时，可按稳定规则标识选一个并告警，这只是容错，不是允许冲突。客户端指定模板也必须在场景授权范围内。

### 3.2 资格与去重

同一模板在不同商品和订单上可以产生不同候选集合，详见[适用规则 PRD](</Users/happyelements/Documents/cashier-admin 2/docs/cashier-payment-availability-prd.md>)。使用可信订单的最终提交支付金额与币种，不单用商品标价；业务限制、商品限制与渠道硬性能力取共同满足范围。方式可用要求至少一条渠道完整支持整单，不能合并各渠道独立区间后误放行其中间隙，也不能拼接不同渠道分别支持的商品属性。

Demo 的纯计算入口为 `src/utils/paymentAvailability.js`，数据为 `src/utils/paymentAvailabilityDemo.js`，页面为 `src/views/payment/PaymentAvailabilityDemo.vue`。仅演示 CNY / USD 两位小数，十进制文本转为最小单位整数，以定价减优惠加税费判断；非法金额、必要事实缺失、币种不匹配不放行。

方式 / 渠道状态为 `available / ineligible / requires_action / temporarily_unavailable / unknown`，available 布尔值为派生字段。原因保留来源、代码、版本、更新时间及可获取的模拟原始结果。只有可用方式进入支付排序，其余按隐藏、待补条件或异常处理。

页面显式传入本地 `createDemoConsultation` 快照（非真实 PSP 响应），检查模板标识 / 版本、订单事实指纹、商户 / 环境及能力版本指纹、查询状态与 120 秒有效期；调用成功与选项 enabled 分开，缺少适用结论为 unknown。支持明确不支持、超时、过期、旧订单模拟，每秒按时间重算，提交时再次检查。无 consultation 参数的计算仅用于静态示例测试，不能作为生产查询降级。草稿与生效规则隔离，显式应用仅复制业务字段并递增版本，不覆盖实时渠道状态；原笔处理中 / 结果未知时本地校验也拒绝发起。

管理页按支付方式、展示策略、测试预览组织。方式侧栏只编辑业务字段；规则和策略草稿由 `applyConfiguration` 先完成整体校验，再同步应用两类本地对象，任一错误均不部分应用。只有发生变化的版本递增；完成后重开预览、清除旧选择，按默认规则模拟首次展示。此处没有后端事务、持久化或线上审批。测试条件及渠道故障与配置草稿分离，统一应用和放弃草稿均不清除故障；`restoreTestEnvironment` 仅显式恢复模拟运行样本与渠道状态，不覆盖规则和策略。

生产须补齐可信订单版本、机构适配和原因映射、商户 / 环境隔离、缓存及撤销、钱包就绪检查、发布回滚、幂等与查单。Demo 无存储、真实支付或自动查询刷新，不替代这些能力。

单笔编排入口 `src/utils/cashierDecision.js` 在适用性之上完成模板兼容检查、一主一备尝试、固定 / 偏好 / 数据排序、回退、标签及默认候选。只对非空可支付集合排序；备用不混入主模板，同名方式的选择仍绑定模板标识。`validateCashierSelection` 每次重判模板归属、原笔状态及所选方式，不执行路由或扣款。

历史样本限定账户、游戏、场景、币种、国家及环境，需授权且在 90 天窗口内，使用确认成功记录；无效返回安全降级。最近本单可用记录用于偏好，标签另核对是否确为该范围最近一次成功。评分样本绑定模板及版本、订单指纹和 120 秒有效期；整体异常回偏好再回固定，单项缺分固定剩余基础位置，同分稳定。均为离线模拟，尚无真实统计或模型契约。

手动选择创建展示锁，绑定订单事实、模板与规则版本、策略版本、方式状态及可用渠道集合；只冻结顺序、标签和展示依据，不冻结资格。相关事实变化使锁失效；主动重新决策可清锁采用新数据，但不覆盖仍有效的选择。默认候选只在显式重开预览时应用，普通重判不再次默认。页面快照和模板尝试仅当前内存可见，不是持久化审计或订单回放。真实备用链配置、授权来源和发布服务仍需生产接入。

方式可支付条件：模板条目启用、方式启用、订单/平台/设备条件满足，且至少一条执行路径符合渠道开关、商户授权、能力和健康要求。

按稳定展示标识去重，不用名称或渠道标识去重。只有用户交互、授权、费用呈现和协议相容的路径才可合并；同名不自动合并。卡品牌通常作为银行卡支持范围呈现，不按 PSP 拆出重复入口。

### 3.3 三种模式的执行顺序

- 固定：基础序号升序。
- 偏好：根据成功历史推断的偏好一项、剩余基础顺序；无有效历史时使用基础顺序。
- 数据：保留历史偏好一项，仅对剩余位置采用可信评分；无有效历史时可对全部可用候选评分。

历史偏好仅提升当前候选中的一项，原位置不再重复展示，不可额外引入模板外方式。同序按基础序号和稳定展示标识决胜。

数据模式默认保护根据成功历史推断的偏好。只有单独批准的实验可将其从固定优先项改为模型特征。当前选择是独立状态，不需要为保留选择而把该项实时移到第一；点击和选中本身不更新历史偏好。

## 四、用户偏好的数据规则

默认使用 `recent_success`；`frequent_success` 为后续可选策略。每次只产生一个推断偏好。

建议作用域：用户、游戏/应用、生产或测试环境、交易市场、币种、明确声明的收银台兼容组。跨范围迁移需另外评审。

- 最近成功：从当前可支付候选中选择窗口内最后成功使用的方式。
- 经常使用：计算时间衰减成功次数 `F(m) = Σ 2^(-成功距今天数 / H)`，同一订单最多贡献一次成功。
- 初始建议窗口为 90 天、半衰期 `H=30` 天；建议至少有 3 笔成功订单，且某方式的衰减成功占比不低于 60% 才称为稳定习惯，否则回到最近成功。以上为待评审起点，不是统计显著性标准。
- 同分按更近的成功记录、基础顺序和稳定标识处理，避免不确定结果。
- 仅使用服务端确认成功；按实际成功时间处理乱序消息，回调去重，测试/欺诈/重复交易按标签剔除或更正。退款不自动抹去用户曾成功使用该方式的事实。
- 偏好仅来自获准使用的有效成功历史，不提供独立的用户设置或保存接口。历史过期后不再参与；退出或切换账户后停止使用相应个人信息，撤回授权不得因缓存继续生效。

## 五、数据排序的计算与验证

### 5.1 演进路线与初始评分

先做同场景分群统计，再评估上下文模型，最后才讨论整套列表优化，不要求首期使用复杂模型或自动探索。

初始代理评分：`S(m,x) = 100 × A(m,x) × B(m,x)`。

- `A`：方式真实可见后，被选为本单首个支付尝试方式的概率。
- `B`：首尝试选择该方式后，该次尝试在观察窗内确认成功的概率。
- `x`：市场、币种、设备、场景、金额段及候选集合等获准上下文，并明确参考位置/排序。

两个估计必须有兼容的条件、周期和事件口径，不能直接相乘不同人群的原始比例。这个分数表示首尝试成功的代理，不是订单最终完成率，不能将各项分数求和代表整套列表价值。实际收益必须通过订单级实验验证。

成本和耗时分别作为预算、体验约束或次级目标，不把百分比、金额、秒数任意加成总分。完成率是否不劣于原策略需预设非劣效检验，置信区间重叠不等于已经等效。成本预算不满足时停用新排序，不以隐藏合法方式替代。

### 5.2 数据口径与置信条件

曝光为本单首尝试前真实可见的订单-方式去重记录，包含位置、候选集合、版本。首尝试后的曝光进入切换漏斗，不混入 A 的分母；服务端返回但未显示不算曝光。

发起按每单首个支付尝试计数，重试不扩充样本。B 只计该次尝试的成功，不将切换其它方式后的成功记回原方式。整单最终完成独立计算。

仅用观察窗结束后的成熟样本。窗口内没有成功只是该代理目标未完成，不直接视为渠道技术失败。回调延迟但实际成功在窗口内时回补；实际成功晚于窗口时进入长期结果，不改写该窗口终点。

小样本可使用兼容父群体先验平滑：`p̃ = (s + k × p_parent) / (n + k)`。先验强度由离线校准确定，不当作真实样本数；A、B 分母不同。最低有效样本、不确定性、时效门槛按市场流量与最小可检测收益设置，加权有效样本量不等于原始条数。

可从小时级更新、7 天与 28 天分窗对照开始评估，最终周期按实际支付时延确定。微小分差保留已批准顺序；无历史批准顺序用基础顺序。渠道健康使用独立实时信号，不等待评分批次。

### 5.3 位置偏差、冷启动与降级

完整记录可见性、位置、候选集和实验分组概率。没有受控数据时，不能把首位的高使用率当成天然偏好，也不能据折叠区低曝光推断其效果差。

受控相邻换位只发生在可调整的位置，设置审批、流量上限和损失预算，不移动受保护的历史偏好或当前选择。具备有效概率和样本覆盖才使用倾向加权等方法，缺少条件不宣称已消除偏差。

- 新用户用获准的群体策略；新方式使用兼容先验或基础顺序，验证后才探索，不把无数据记为零分。
- 细分群证据不足时，可去掉金额段或浏览器小版本等维度；国家、币种、支付形态不能未经验证直接混池。无可迁移先验时用基础顺序。
- 部分方式无可信分数时，其原槽位保持不动，仅重排可信项槽位；覆盖不足或可信项少于两项时，剩余区整体回退。
- 评分超时、过期、关键输入缺失或版本不兼容时回偏好策略；个人历史也不可用时回基础顺序。所有降级保留原因，安全资格检查不随之放宽。

### 5.4 在线实验

埋点对账与 A/A 检查后，先只记录建议不改变展示，再小流量随机验证，按预设条件放量并保留长期对照。

固定与偏好、偏好与数据分别比较；候选范围、页面、标签、默认选中保持一致。用户在实验周期内稳定分组，游客采用获准的会话/订单标识，不做指纹识别。

同一用户多单需采用用户级聚类等分析方法，不假设每单独立。样本量、最小收益、期限、观察窗、分层分析和停止规则事先约定，防止中途挑选有利分组。

主指标为去重订单的最终支付完成率，辅助看首尝试成功、耗时和成本；退款、拒付等需更长观察。重复扣款、安全规则突破立即止损；完成率、延迟、成本按预设门槛回滚。回滚仅影响新决策，不重发已受理交易。

## 六、会话、交易与发布安全

首次决策保存配置版本、模板、初始顺序和实验分组。订单金额/币种、必要地区信息变化、主动刷新或快照过期时重新决策，保留仍合法的用户选择；紧急禁用始终覆盖快照。

支付提交前服务端复核资格。已受理交易按原尝试查单；超时、未收到回调或状态未知时不自动换渠道。只有确认未提交或原尝试已终态失败且允许重试，才另行评审安全重路由，包括失败码白名单、限次及幂等规则。

同一支付尝试重试使用同一幂等标识，新尝试先查订单已支付状态；另需防止跨渠道并发扣款，不能只依赖单渠道幂等键。禁用只影响新尝试，不阻断原交易回调、查询与对账。

发布以规则、模板引用和策略版本形成一致快照，校验默认/备用兼容性、同级冲突、重复展示标识、基础序号、执行路径、配置有效期及推荐真实性。静态校验不替代运行时检查。

关闭前展示受影响场景，普通操作不能静默清空支付能力。紧急止损可以强制关闭，但保留警示、审批权限、审计和告警。恢复旧配置不能恢复被安全紧急禁用的路径。

## 七、追踪与验收清单

记录 `decision_id`、会话、订单、策略/模板版本、规则命中和模板尝试链、候选与排除原因、基础及最终顺序、标签及默认选择。偏好/数据模式再记录偏好快照引用、是否因历史偏好提前、统计/模型版本、特征引用、分群、数据截止、评分及不确定性、实验概率和降级原因。

事件包括 `cashier_view`、`method_impression`、`method_select`、`payment_attempt`、`payment_result`，关联订单和支付尝试；客户端行为与服务端最终结果分开，成功不只信客户端回传。

原因码示例：`RULE_MATCHED`、`SCENARIO_DEFAULT`、`TEMPLATE_EMPTY`、`CURRENCY_UNSUPPORTED`、`DEVICE_UNSUPPORTED`、`METHOD_DISABLED`、`CHANNEL_UNAVAILABLE`、`LAST_SUCCESS_BOOST`、`FREQUENT_SUCCESS_BOOST`、`DATA_SCORE`、`INSUFFICIENT_EVIDENCE`、`SCORE_TIMEOUT`、`BASE_ORDER`。

不保存完整卡号、支付令牌及无必要个人信息，明确访问权限和保存期限。运营解释页面使用“上次成功提升”“同场景数据调整”“证据不足保持原序”，不向用户展示内部概率或成功承诺。

重点验收：

1. 禁用、维护和不兼容方式不因历史偏好进入可支付列表。
2. 默认/备用不跨游戏、币种、授权或支付形态；首个模板为空时能正确尝试下一项。
3. 同级冲突阻止发布，历史偏好提前后不在原位置重复展示，排序第一不自动改变标签或选择；不提供用户偏好设置入口或保存接口。
4. 一笔成功只支持最近成功参考，不直接满足稳定习惯要求；重复回调不增加偏好次数。
5. 无个人历史可使用群体排序；缺分、超时和过期按约定回退，不混排基础序号与分数。
6. 用户已选/填写信息时不重排；仅点击或选中不更新历史偏好；切换账户或撤回授权后不读取旧历史。
7. 提交前遇紧急关闭会拦截；已提交超时查原笔，不创建第二笔扣款。
8. 配置异常时仅使用批准范围和有效期内的历史发布快照，叠加当前安全检查；无可靠资格来源则不发起支付。

## 八、成功指标的统计与验收口径

### 8.1 基准人群、时间与结果

以订单第一次发起收银台启动请求为进入时点，并在本次排序结果生成前完成实验分配。业务分母为当时有效、未支付、纳入该场景的去重订单；页面未成功渲染、决策失败、零可用方式或之后主动离开的订单仍计入原组。进入前已失效、已支付、测试等排除规则须事先固定，不按实验后的结果选择性删单。

同一订单多次打开只计一次，重试和切换方式均归属首次实验分组；跨会话也不能因换排序而重记。订单成功使用任一合法方式即可贡献一次整单完成，不能只把采用排序推荐方式的成功计入。

主观察窗 `W` 从首次启动请求开始。按各支付市场的到账周期预先确定，同一对照实验保持一致；异步到账方式必要时另设分层实验。报表只用观察窗已结束的订单，不把较新订单直接算失败。窗内无成功为该窗未完成，不等同于技术失败；回调延迟按实际支付成功时间回补，窗外成功另报长期结果。

成功以支付服务与渠道确认的统一交易状态为准，状态映射需支付团队确认；若授权、扣款和结算不同步，不能把仅授权当作已付款。后续退款/拒付单独记录，不直接抹去原始付款事实。

### 8.2 业务与体验指标

| 指标 | 分子/分母或计时口径 |
| --- | --- |
| 整单付款完成率 | `W` 内成功付款订单数 ÷ 进入收银台有效订单数；以首次分组归因 |
| 支付发起率 | `W` 内至少创建一个实际支付尝试的订单数 ÷ 进入收银台有效订单数；单纯点击按钮不算已发起 |
| 首次尝试成功率 | 首个实际支付尝试在 `W` 内成功的订单数 ÷ `W` 内有实际支付尝试的订单数；换方式/重试后成功只计整单完成 |
| 支付方式确认耗时 | 首次方式列表可操作至首次人工选择或确认方式的时长；默认预选不触发确认；仅已确认订单报 P50/P90，同时报告确认覆盖率及未发起比例 |
| 方式切换率 | `W` 内人工先后选择至少两个不同展示方式的订单数 ÷ 至少有一次人工方式选择或确认的订单数；自动预选和系统降级不算切换 |
| 历史方式使用率 | 首次实际尝试使用历史优先方式的订单数 ÷ 首次决策有有效可用历史优先方式的订单数；分母包含未发起订单 |
| 完成付款耗时 | 首次启动请求至实际付款成功的时长；仅窗内成功订单报 P50/P90，并同时展示整单完成率，避免只保留快单 |

确认覆盖率为至少一次人工选择或确认方式的订单数除以成功展示可操作列表的订单数。核心整单完成率仍保留所有启动订单，不能因为确认或耗时统计需要而缩小核心分母。

相对提升为 `(实验组完成率 - 对照组完成率) ÷ 对照组完成率`；百分点差为两组完成率直接相减。对照完成率为零时不报告相对提升，仅报样本和百分点差；任一组没有有效样本时显示“暂无数据”，不计算差异。缺失或未成熟数据不能填为 0。

### 8.3 护栏口径

- 重复扣款：同一订单存在多笔独立、经确认的有效扣款，不是同一交易的重复回调；记录事件数和受影响订单数。结论不能只依赖前端埋点。
- 非法展示/发起：违反当时的商户授权、平台或订单能力约束，或未经用户确认发起支付的事件数。目标为本功能归因事故 0。
- 零可用方式率：首次决策正常结束但可支付方式为零的订单数 ÷ 核心启动订单数；加载失败另报，不能把缺失决策当作零方式，也不能从核心分母删除。
- 列表加载失败率：规定展示时限内未获得可操作列表或明确无方式状态的订单数 ÷ 核心启动订单数；包含客户端渲染、接口超时等失败，允许单独分解原因。
- 降级率：首次启动因策略/数据服务异常采用备用排序的订单数 ÷ 核心启动订单数；无用户历史导致使用基础顺序不算异常降级。
- 展示响应耗时：从启动请求至列表可操作或明确无方式的端到端时长，报 P95/P99，同时报告超时失败率；未返回请求不能从失败率消失。
- 单笔成功支付成本：同一成熟订单群的全部支付处理费用（含失败尝试费用）÷ 成功订单数，分币种计算；跨币种汇总需固定汇率。未到账费用标估算并后续对账，不能当作零成本。
- 退款/拒付：在事先确定的长期观察窗内，按成功付款订单计算订单比例，并另报金额比例；不同批次成熟程度一致后再比较。
- 支付结果未知率及投诉：分别按有实际尝试订单、核心启动订单统计，固定未知状态的判定时限、投诉标签和归因规则，不能将用户取消直接当系统异常。

### 8.4 数据准备与放量判定

在本项目尚无真实交易基线的前提下，正文中的“完成率相对提升 1%”“确认耗时中位数降低 10%”仅为建议目标。产品、支付、数据团队需根据历史分布、最小业务收益和流量冻结正式值；技术侧同时确定加载时限、服务可靠性、最大可接受损失和成本预算，不将这些值视为现成承诺。

实验前补充可操作列表展示、人工方式确认、错误/超时/降级事件，与现有启动、尝试、付款结果按订单和决策标识关联。先核对客户端漏报、服务器订单对账、实验分配比例、版本一致性及样本去重；严重缺失时不能做收益判断。

固定方案主要验证功能正确及不劣；偏好方案重点看有有效历史用户的确认耗时，并检验整单完成率非劣及发起率等护栏；数据方案看相对偏好方案的整单完成率提升。无历史用户、新老用户、市场/币种、设备和金额段做预先定义的分层观察，不能只报获益人群。

收益结论要同时达到预设业务目标与统计检验要求。非劣需使用事先定义的非劣界值和足够把握度，不能以“差异不显著”证明无损失；多次查看和分层比较按预先约定的方法处理，不能无限观察到达标为止。长期风险未成熟时仅允许受控放量并保留观察，不能宣布所有安全护栏已通过。

上线看板至少展示基线、当前值、相对变化/百分点变化、有效样本、观察窗、实验与配置版本、分层结果和护栏状态。未达到相应阶段目标、关键人群出现不可接受损失、数据质量不合格或护栏超限，均不能因局部点击/首尝试指标好看而放量。

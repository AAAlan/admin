# 收银台支付方式排序与决策方案

版本：V1.1 产品建议稿 · 2026-10-26

本次补充：用户偏好排序、数据驱动排序、统一优先级、评分与冷启动、实验与降级，以及配套后台字段和验收场景。

## 1. 结论与适用范围

建议采用“规则决策 + 模板基础排序 + 运行时可用性过滤”，先做到可控、可解释、可回滚，再引入用户偏好和动态优化。

完整流程：确认订单与场景 → 匹配策略/模板 → 过滤不适用方式 → 对展示方式去重 → 排序 → 决定推荐与默认选中 → 用户确认支付 → 选择执行渠道 → 支付结果与异常处理。

本方案适用于当前游戏支付管理后台的国内/海外、自建 Web/原生收银台。平台 IAP 是否开放第三方方式，由平台政策、合同和业务合规规则先行决定，不能通过排序规则绕过。

本次交付产品与逻辑方案，不实现页面，不接入真实交易，不假定已有实时成功率、费率或用户画像服务。下文未注明“现状”的能力均为建议新增。

### 1.1 产品目标

- 用户：尽快找到当前能用、自己愿意使用的支付方式，付款失败后有明确下一步。
- 运营：明确控制不同场景的展示顺序、推荐内容及生效范围。
- 支付团队：满足合规和可用性约束，在成功率、体验与成本之间做可验证的优化。
- 研发/客服：能够回答“为什么看到这个顺序、为什么没有某方式、当时走了什么策略”。

目标优先级：合规与资金安全 > 能完成支付 > 用户明确选择与体验 > 业务推广和成本优化。

### 1.2 必须分开的六个概念

| 概念 | 决定什么 | 示例 |
| --- | --- | --- |
| 模板决策 | 使用哪套候选方式及基础顺序 | 命中 USD 移动端模板 |
| 可用性决策 | 本次请求能展示/使用哪些方式 | 当前浏览器不支持某钱包，剔除 |
| 展示排序 | 可用方式按什么顺序出现 | PayPal、银行卡、本地钱包 |
| 推荐标签 | 哪些方式展示什么推荐信息 | “推荐”“上次使用” |
| 默认选中 | 首次进入时展开或选中哪一项 | 默认展开第一项，但不自动付款 |
| 渠道路由 | 用户选定方式后，实际由谁处理 | 银行卡由已批准的某 PSP 商户账户处理 |

排序第一不等于有推荐标签；有推荐标签不等于默认选中；默认选中不代表取得扣款授权；展示银行卡不意味着必须固定使用某一家 PSP。

### 2.2 需要补齐的规则

1. 当前解析 Mock 使用首个精确匹配，再尝试场景默认和已关联模板；默认和关联兜底分支未重新校验请求币种/环境等兼容性。正式方案必须对所有兜底候选重复执行硬约束检查。
2. 同条件多模板的选择不能取决于列表返回顺序，要有显式优先级与冲突校验。
3. 模板编辑页已不使用国家字段作为新配置条件；国家、人群等差异建议放入场景决策规则，不重新塞入模板唯一标识。
4. 当前“推荐”是内容配置。若需要影响排序，应新增明确的排序策略，不能悄悄改变原有字段含义。
5. 维护/禁用/渠道关闭/模板关闭需有统一的运行时解释，不能只影响后台选择器。
6. 当前国内场景描述中的原生/Web 含义与历史布尔字段不完全直观。上线前应梳理统一业务枚举，不直接用 `is_web_cashier` 推断商店 IAP 或平台合规性。

## 3. 决策所需输入

| 输入 | 用途与来源 | 缺失处理 |
| --- | --- | --- |
| 游戏/应用、业务线、生产或测试环境 | 后端订单与接入身份；隔离配置和商户权限 | 必填，不能从其它游戏或环境兜底 |
| 支付场景、平台、收银台形态、设备环境 | 场景标识和后端接入配置；决定允许的支付路径 | 无法确认时拒绝不安全路径 |
| 订单金额、订单支付币种、交易类型 | 后端订单；判断限额、一次性/订阅等能力 | 必填；金额使用最小货币单位 |
| 模拟器标识 | 区分设备兼容策略 | 与生产/测试环境分开，不能互相替代 |
| 付款国家/地区 | 市场适用性和合规校验 | 使用经业务验证的交易国家；IP/语言只作辅助，不能单独作为合规依据 |
| 钱包/浏览器/SDK 能力 | 判断调用方式是否可用 | 未知时按该方式要求探测；必要能力未确认不可选 |
| 已登录用户标识、显式偏好及成功历史 | 后续偏好排序；限定授权用途和保留期限 | 不消费无授权个人历史；无历史时使用获准的群体策略或基础排序 |
| 渠道及商户账户运行状态 | 判断是否至少存在一条安全可用执行路径 | 未知时按预先批准的健康数据有效期和降级策略处理 |

首期不需要一次接入所有画像。涉及订单、商户权限、合规的事实以后端为准；客户端仅上报设备能力，服务端仍需复核。

## 4. 先决定使用哪个模板

### 4.1 配置结构

保留“全局模板库 + 场景关联”，在场景关联层增加“决策规则”。

- 模板保存候选展示方式、基础顺序、标签及默认选中策略，供多个场景复用。
- 场景规则保存条件、优先级、生效时间和目标模板。
- 国家、金额段等条件放在规则层；支付能力范围在方式/渠道能力层维护，不通过复制大量模板表达。
- MVP 条件限定为国家/地区、币种、设备环境和模拟器状态；金额段与用户分群后续扩展。固定维度不提供自由脚本。

### 4.2 确定性匹配规则

先限定候选范围：同应用/业务线/环境、当前场景已关联、已发布、时间有效。模板币种、收银台形态、必要设备约束必须与订单兼容。

按以下顺序尝试，不合格的候选不得进入下一步：

1. 命中场景条件规则：按 `priority` 从小到大；数字越小优先级越高。
2. 当前场景中、当前兼容范围的默认模板。
3. 当前场景中显式配置的兼容备用模板，按 `fallback_order` 从小到大尝试。
4. 均不可用：返回“暂无可用支付方式”，记录并告警。

每个候选还需运行方式可用性检查；若可支付方式为零，则记录 `TEMPLATE_EMPTY` 并继续下一候选。选定某模板后不拼接其它模板的支付方式，避免隐式扩大业务授权范围。

硬规则：

- 不得跨订单支付币种、游戏、生产/测试环境、平台政策或商户权限兜底；需要换币时必须重新报价并取得用户确认，属于另一条业务流程。
- 默认模板只代表“无更高优先规则时尝试”，不代表可以跳过兼容性检查。
- 现有场景单一默认模板可保留，但币种不兼容时不适用；通过备用顺序覆盖其它币种，不暗中自动换币。
- 发布时禁止同一范围内、同优先级且可能同时命中的规则；不依赖“条件越多越优先”的隐式解释。
- 若历史脏数据仍冲突，运行时按稳定 `rule_id` 选一个并告警；这是容错，不是允许冲突的产品规则。
- 显式请求模板 ID 也只能在当前场景授权范围内生效，不能接受客户端任意指定。

## 5. 再决定哪些方式可以展示与支付

### 5.1 状态与处理

| 条件 | C 端处理 | 可选/推荐/默认选中 |
| --- | --- | --- |
| 模板条目关闭、方式禁用、未获商户授权 | 不展示 | 均否 |
| 不支持订单币种/国家/交易类型，或金额不满足限额 | 不展示；必要时提供明确的业务提示 | 均否 |
| 平台不允许、设备/浏览器无必要能力 | 不展示 | 均否 |
| 存在至少一条已批准、健康且兼容的执行路径 | 正常展示 | 可以，仍需排序与选择策略决定 |
| 方式维护或所有执行路径临时不可用 | 默认隐藏；开启维护展示时置灰置底，说明“暂不可用” | 均否 |
| 必要付款信息未填写，如交易国家尚未知 | 引导补充后重新决策；不猜测可用范围 | 暂不选择 |

“维护展示”只针对原本符合业务资格的方式。违反合规或未授权的方式不能以置灰形式展示。若一个可支付方式也没有，维护项只能作为说明，不能伪装成可支付列表。

方式可支付条件：模板条目启用 AND 方式启用 AND 订单/平台/设备条件通过 AND 至少一条执行路径满足渠道、账户、能力与健康约束。

任意一层禁止均优先于推荐、置顶、历史偏好。临时开关只影响新支付尝试，不中断已受理交易的查询、回调和对账。

### 5.2 同类方式去重

新增稳定的 `display_method_key` 表示用户理解的支付入口，例如 `card`、`paypal`；不要依赖大小写可变的 `pay_name` 或渠道 ID 去重。

- 同一展示方式下可关联多个候选执行路径；关闭一条路径不等于关闭整个方式。
- 只有用户交互、授权要求、费用呈现与商户协议相容时才允许合并；不能因名字相似就自动合并。
- 卡品牌默认作为银行卡方式的支持范围/图标，不按 PSP 拆成重复入口。
- 首期可继续绑定单渠道，不要求立刻建设智能路由；仅在完成映射确认后合并历史条目。

## 6. 排序、推荐与默认选中

### 6.1 排序模式

首期提供“固定排序”；后续增加“用户偏好排序”，最后才考虑数据驱动排序。

| 模式 | 适用场景 | 排序逻辑 |
| --- | --- | --- |
| 固定排序（P0） | 所有场景；无历史数据的安全基线 | 过滤后按模板 `sort_order` 升序；空位自然前移 |
| 用户偏好排序（P1） | 已登录且允许使用支付偏好的用户 | 用户显式偏好 → 有效运营置顶 → 推断偏好一项 → 其余基础顺序 |
| 数据驱动排序（P2） | 数据充足、已完成实验验证的市场 | 默认保留上述锁定项；其余方式按数据评分排序；成本作为约束或次级目标 |

每层内部按基础顺序，同序用稳定 `display_method_key` 决胜。同一方式只占一个最高优先层，不重复展示。未进入候选模板的历史方式不得被补进列表。

P1 具体约定：

- 运营置顶最多一项，必须配置范围、起止时间；置顶只是排序，不保证出现，不保证默认选中。
- 最近成功方式只使用服务端确认成功的结果，不使用“最近点过”或“曾发起”。建议初始保留窗口 90 天，最终由隐私政策与数据评审确定。
- 用户偏好需按可兼容的业务范围使用；跨游戏、跨国家/币种使用不能默认开放。
- 无历史、历史过期或历史方式不可用时，忽略该层，不报错，不引入其它支付方式；无个人历史不等于不能使用获准的群体数据排序。
- 新渠道/新方式没有历史数据时沿用运营基础顺序，不能默认认为其成功率为零。

### 6.2 推荐标签

- 保留现有 `is_recommended` 与文案语义：只决定是否显示标签，不改变顺序。
- 推荐仅对可支付方式生效；维护项不展示推荐标签。
- 允许多个推荐项以兼容现有配置，新增发布警告；建议一个场景主推一项，确有不同适用价值时再配多项。
- “上次使用”是历史事实标签，不应冒充业务推荐。
- “手续费低”“优惠”等必须对用户当前订单真实成立；商户成本低不能宣传为用户手续费低。
- 多语言按用户语言 → 配置默认语言 → 通用“推荐”处理；不能显示翻译 key 或未经验证的优惠承诺。

### 6.3 默认选中

建议配置三个选项：不预选、选中排序第一项、优先最近成功方式（P1）。

- 默认建议采用“不预选”；若界面是单项展开式、支付按钮信息明确且用户仍需主动确认，可按场景选择“选中第一项”。
- 最近成功策略：最近成功且仍可支付则选中，否则选第一可支付项；无可支付项则不选。
- 用户在本次会话明确选择后，该选择优先；不因后续排序/推荐计算覆盖它。
- 用户选择失效时取消选择，解释原因并请用户重新选择；不要在无提示情况下切到另一方式付款。
- 选中只代表界面状态，不自动调起、不自动扣款、不自动勾选授权。

### 6.4 会话稳定性

首次决策记录会话快照：配置版本、选中模板、初始顺序和实验分组。普通配置更新不使正在操作的列表跳动。

允许重新决策的情况：用户主动改变影响资格的订单/地区信息、订单金额/币种变化、用户主动刷新、快照过期。应保留仍然合法的用户选择。

紧急禁用和安全约束始终覆盖快照；支付提交前服务端重新校验当前资格。已受理交易按原尝试追踪，不套用新配置重发。

### 6.5 用户偏好排序：具体产品与逻辑

目的：让用户更快找到自己愿意使用的方式，不把一次误点或一次渠道故障永久固化成偏好。

#### 6.5.1 偏好信号与作用

| 信号 | 可信度与用途 | 不应该做什么 |
| --- | --- | --- |
| 用户主动设置“优先展示此方式” | 最高优先的跨会话偏好，最多一项；允许修改和清除 | 不自动授权、绑定卡或发起支付 |
| 服务端确认的最近成功方式 | 默认推断偏好；反映最近一次成功完成的路径 | 不把“调起成功”当作付款成功 |
| 近期成功使用频率 | 可选的习惯模式；用于多次支付用户 | 不按失败重试次数或订单金额判断喜好 |
| 本次会话主动选择 | 只控制当前选择状态；未经确认不写成长期显式偏好 | 不因排序异步返回覆盖该选择 |
| 点击、发起、取消、绑卡、安装钱包 | 可用于分析或后续获准的模型特征，初期不独立提升排序 | 不将取消或银行拒绝直接解释为“不喜欢” |

显式设置入口仅在启用个性化的场景出现，说明保存范围，并提供“恢复默认”。采用固定排序的场景不读取跨会话偏好，不应让用户误以为设置会全局生效。

历史作用域初始建议：同一用户 × 游戏/应用 × 生产或测试环境 × 交易市场 × 币种 × 收银台兼容组。兼容组必须由配置明确声明，不自动跨游戏或跨市场迁移。

游客不跨设备识别，不使用设备指纹推断同一人；未登录时可保留当前会话选择，但不读取其他账户历史。退出、切换账户、撤回相关授权或清除偏好后停止使用相应个人信息。

#### 6.5.2 两种推断偏好模式

默认采用 `recent_success`，后续可以按场景选择 `frequent_success`；同一次决策只生成一个推断偏好锚点。

1. 最近成功：在当前候选方式中，取有效窗口内最近一次服务端确认成功的方式。最近一项不可用时，可继续找仍在窗口内的上一可用成功方式，而不是把不可用方式补进列表。
2. 成功习惯：对每项方式计算时间衰减成功次数 `F(m) = Σ 2^(-成功距今天数 / H)`。同一订单最多贡献一次成功；渠道回调按事件去重。
3. 习惯模式需有最低证据：建议起点为有效窗口内至少 3 笔成功订单，且某方式的衰减成功占比不少于 60%；否则回退最近成功模式。这只是防止一笔交易被称为“习惯”的产品门槛，不是统计显著性结论。
4. 初始建议窗口 90 天、衰减半衰期 `H=30` 天，均须经隐私和业务评审确定。窗口外历史不再参与；显式偏好由用户维护，另行适用保存政策，不能与推断历史混为一谈。
5. 服务端成功状态落库后异步更新聚合；按交易实际成功时间而非消息到达时间判断最近一次。历史退款不自动推翻“用户曾选择并完成支付”的事实；欺诈/测试/重复交易按标签剔除或更正。

#### 6.5.3 排序算法与边界

可支付集合过滤和去重后，依次取：

1. 有效显式偏好 `E`，最多一项。
2. 有效运营置顶 `O`，最多一项；与 `E` 相同时不重复。
3. 推断偏好 `I`，最多一项；与已取项相同时不重复。
4. 剩余项按模板基础顺序。

因此用户主动表达的偏好优先于业务推广；运营置顶优先于系统推断，但不能清除或改写用户保存的偏好。若必须固定某支付路径，应通过明确的场景资格/业务流程处理，不伪装成个性化排序。

某偏好方式不可用时只跳过，不自动删除用户设置，也不偷偷替换成另一 PSP 对应的不同授权方式。恢复可用后，下次会话可再次按偏好提升。

若一个场景只有两三项，锁定项已占满，则偏好模式无需再做复杂打分。排序结果与默认选中策略仍独立；显式偏好表示“优先展示”，不是“自动选择并付款”。

### 6.6 数据驱动排序：具体产品与逻辑

目的：在保证安全和尊重用户选择的前提下，提高整个收银台的订单支付完成率，不单独最大化点击率或最低费率。

#### 6.6.1 三个递进版本

| 版本 | 决策能力 | 上线前提 |
| --- | --- | --- |
| D1 分群统计排序 | 按市场、币种、设备、场景等群体特征，对未锁定候选评分 | 曝光与支付结果完整；成熟样本、位置偏差处理和在线实验到位 |
| D2 上下文模型排序 | 加入订单金额段、设备能力，以及获准的历史聚合特征 | 特征服务、校准、训练/验证隔离、模型版本与可解释输出 |
| D3 整体列表优化 | 评估整套列表带来的订单最终完成，包括切换和替代效应 | 足够随机实验数据、列表级评估与长期监控；不将单项概率相加 |

初期只做 D1，不要求直接引入机器学习或多臂老虎机。D2/D3 为后续演进，不承诺模型必然优于规则。

#### 6.6.2 排序评分建议

先估计两个在可比位置、可比场景下的概率：

- `A(m,x)`：方式真实可见后，用户将它作为本单首个支付尝试方式的概率。
- `B(m,x)`：首个支付尝试选择该方式后，该次尝试在观察窗内服务端确认成功的概率。
- 初始候选分数 `S(m,x) = 100 × A(m,x) × B(m,x)`。

`x` 表示市场、币种、设备、场景、金额段，以及当时的候选集合等经批准的上下文；估计还需明确参考位置/排序。两项需来自相同事件定义和参考位置下的兼容估计，不能把不同人群、不同周期的两个原始比例直接相乘。

这个分数是“该方式带来首尝试成功的可能性”的代理指标，不是整单最终支付完成率；用户可能换方式成功，各方式的选择还会互相影响。生产决策必须通过订单级随机实验确认收益；D3 才直接学习整个排序对最终完成的影响。

例：仅比较两个未锁定候选，A 方式预计首尝试选择率 50%、该次成功率 80%，分数为 40；B 方式分别为 30%、95%，分数为 28.5。A 可以排在 B 前面，说明不能只按 95% 与 80% 的原始成功率排名。数值仅为公式示例，不代表真实效果。

成本与体验处理：

- 主目标是订单支付完成率，完成耗时和用户操作负担作为共同评估指标；不要任意混合“成功率百分比、手续费金额、秒数”生成不可解释总分。
- 运营设置的成本预算用于限制“是否启用新的排序策略”，不用于把合法可用方式偷偷隐藏。预算不满足时回退已批准的排序策略。
- 只有经过预设非劣效实验确认完成率不明显变差，才可在该约束内选择成本更低或耗时更短的排序；置信区间重叠不代表已经等效。
- 不使用用户敏感属性推断支付意愿，也不做个性化价格或限制可用方式。历史渠道费率无法代表本次商户账户和订单的实际成本。

#### 6.6.3 数据口径、平滑与置信门槛

- 曝光口径：本单首次发起支付前，实际可见的订单-方式去重记录，带位置、候选集合和模板版本；服务端返回但未显示不算曝光。首尝试后的曝光另记切换漏斗，不能混入 A 的分母。
- 发起口径：每个订单的首个支付尝试；失败重试不扩充首尝试样本量。最终完成率仍按订单另行计算。
- 成功口径：该次首尝试在约定观察窗内服务端确认成功；换另一方式成功不能记到原方式的 `B`。
- 只用观察窗已结束的成熟样本，训练/验证按时间划分；同一用户/订单重复出现需防止泄漏。观察窗内未成功属于该代理目标的未完成，不因此直接标记为“渠道技术失败”；后续延迟回调需更正相应报表。
- 小样本使用同口径父群体先验平滑，例如 `p̃ = (s + k × p_parent) / (n + k)`；`k` 是先验强度，由离线校准确定，不能当真实样本数。A、B 的分母分别是有效曝光和有效首尝试，不能共用。
- 每个分群配置最低有效样本、最大不确定性和数据新鲜度门槛；门槛依据流量、方差、最小可检测收益确定，不设一套全市场通用阈值。经加权后的有效样本量不能直接用原始记录数代替。
- 建议从小时级批量更新、最近 7 天与 28 天分窗对照开始；窗口、刷新频率和过期时间按市场支付周期校准。健康熔断使用独立的实时安全信号，不等统计排序下批更新。
- 微小分差或证据不足时保留上一已批准顺序；首次没有已批准顺序则用基础顺序。只有超过预设调整门槛才发布新排序，避免频繁来回翻转。

#### 6.6.4 位置偏差与冷启动

不能直接将“排第一获得更多点击”解释为用户更喜欢，也不能将长期折叠项的低使用率解释为差。必须保留展示位置、可见性、当时完整候选集和流量分组。

- 有足够证据时，在合规、未锁定候选内做受控相邻换位实验，估计位置影响；不移动用户显式偏好、运营锁定项，也不触碰当前选择。
- 记录分组概率；只有具备有效随机化/倾向概率和样本覆盖时，才使用倾向加权等去偏方法。没有这些条件，不宣称历史数据已经消除偏差。
- 折叠区没有真实曝光的候选，不可直接外推其首位选择率；需受控曝光或回退基础顺序。
- 新用户：不使用个人历史，但可使用获准的同场景群体排序；群体证据不足则基础排序。
- 新方式/新市场：采用经验证的兼容父群体先验和基础顺序，不把无样本记为零分；先完成能力与支付闭环验证，再给少量受控探索曝光。
- 分群回退从细粒度向兼容的粗粒度收缩，例如去掉金额段、浏览器小版本；国家、币种和支付形态差异不能未经验证直接混池。没有可迁移先验时回到基础顺序。
- 探索与扩大实验分开审批、设流量上限、退出条件和损失预算；仅在无锁定剩余区进行，不为收集数据向用户展示不可用方式。

#### 6.6.5 统一排序与降级

数据模式的默认顺序：用户显式偏好 → 有效运营置顶 → 推断偏好一项 → 其余按 `S` 降序。用户本次选择始终保留，但不需要把选中项实时拖到第一。

若锁定项占满列表，则模型仅记录建议，不声称改变了排序。只有经单独批准的实验，才允许把“推断偏好”从锚点变成模型特征；显式偏好仍不被覆盖，实验必须单独评估老用户体验。

降级规则：

1. 评分服务超时、快照过期、关键数据缺失、模型版本不兼容：停止采用数据分数，回到用户偏好模式。
2. 个人偏好服务也不可用或不允许使用个人历史：回到运营置顶（若本模式允许）与基础顺序；不阻塞打开收银台。
3. 服务正常但某一候选无可信分数：只对有可信分数项原有的槽位重排；未知项保持原槽位，不混排“分数”和“基础序号”。覆盖不足或仅剩一个可信项时整组回退。
4. 硬资格/安全校验不可用时，不能借排序降级放行；仍遵守原方案的安全降级边界。
5. 同分按基础顺序和稳定 key 决胜；所有降级输出原因，不能只展示“智能排序失败”。

### 6.7 实验、解释与后台配置补充

#### 6.7.1 验证路径

埋点对账与 A/A 检查 → 影子排序 → 小流量随机实验 → 按预设门槛逐步放量 → 保留长期对照。

- 分开比较：固定排序与偏好排序、偏好排序与数据排序。各组保持候选范围、页面、推荐标签及默认选中策略一致，避免把其它改动的效果算给排序。
- 同一用户在实验周期内稳定分组，游客按获准的会话/订单标识分组，不做指纹识别；跨会话用户分析应采用用户级聚类等方法，不能把其多笔订单当完全独立样本。
- 按新老用户、市场/币种、设备、金额段做预先约定的分层观察。预设样本量、最小可检测收益、观察窗、实验期限和停止规则；不中途挑选有利分组宣布胜出。
- 主指标仍为订单最终支付完成率；首次尝试成功、完成耗时、成本是辅助指标；拒付/退款等滞后指标需更长观察，初期转化提升不能替代长期安全判断。
- 零可用方式、重复扣款、安全规则突破属于立即止损；完成率下降、延迟/成本恶化按预设统计和业务门槛回滚。回滚只改变新决策，已受理交易继续按原尝试查询。

#### 6.7.2 后台新增字段与解释

| 配置组 | 字段与约束 |
| --- | --- |
| 排序模式 | `fixed / preference / data_driven`；场景覆盖模板时必须显式展示继承关系，禁止隐式多处生效 |
| 偏好策略 | `preference_source=recent_success/frequent_success`、历史窗口、半衰期、最低成功证据、保存作用域；首期采用平台级安全默认，不全部开放给运营自由调参 |
| 用户偏好保护 | `protect_inferred_preference` 默认开启；显式偏好始终保护；关闭推断保护需实验与复核 |
| 运营置顶 | 方式 key、范围、有效期；最多一项，置顶冲突阻止发布 |
| 数据策略 | `ranking_policy_id/version`、特征与分群版本、有效期、覆盖和置信门槛、排序更新门槛；不提供任意脚本 |
| 实验与降级 | 实验 ID、流量比例、分组单位、对照策略、告警与回滚规则、兜底链、评分响应预算 |

决策解释增加：偏好来源/有效期、锁定层、每项基础名次与最终名次、分群层级、数据截止时间、模型/统计版本、A/B 估计与不确定性、代理分数、探索标识、降级路径。面向普通运营显示“最近成功提升”“同场景数据提升”“证据不足保留基础序”，不把内部概率显示成对用户的成功承诺。

生产日志记录用于复现的特征快照引用及版本，不长期保留不必要的个人明细。用户撤回授权后，新请求不得因缓存继续使用个人偏好。

## 7. 支付执行与失败处理边界

支付方式排序是 C 端展示决策；执行渠道选择是支付服务决策，配置上分开管理。

P0：用户选定展示方式后使用其配置的、当前有效执行路径。P1 以后在明确具备多渠道能力时才引入渠道优先级、健康熔断和成本优化。

| 结果/状态 | 行为 |
| --- | --- |
| 调起前发现方式不可用 | 阻止发起，提示“该方式暂不可用，请重新选择”，刷新资格 |
| 用户取消 | 返回收银台并保留选择；不统计为渠道技术故障，不自动重试 |
| 已确认终态失败 | 按失败原因提示，可建议其它方式；用户主动确认后创建新的支付尝试 |
| 超时、回调未到、状态未知、处理中 | 提示查询中，使用原支付尝试查单；不自动换渠道或创建另一笔扣款 |
| 成功 | 以服务端确认结果更新订单和最近成功方式，关闭重复支付入口 |

只有支付服务明确确认“尚未向渠道提交”或“原尝试终态失败且允许重试”时，才讨论安全重路由；限次、失败码白名单和幂等策略需另行评审。

同一订单应由服务端防止并发重复扣款；单次支付尝试的重试使用同一幂等标识，新尝试也必须先检查订单已支付状态。仅配置幂等键不足以解决跨渠道重复支付。

## 8. 后台产品结构

不新增一个包罗所有能力的“大决策页面”，沿用三个入口并补一个诊断工具。

| 入口 | 操作与核心信息 |
| --- | --- |
| 全局收银台模板 | 继续添加/拖拽/启停方式、编辑推荐；增加排序模式、默认选中策略；展示方式与执行渠道分层 |
| 支付场景 → 收银台决策 | 关联模板、条件规则、优先级、生效时间、默认模板、备用顺序；显示覆盖范围与冲突 |
| 支付方式/渠道 | 维护能力、授权、状态与健康；关闭前展示受影响游戏/场景/模板，提供紧急停用 |
| 决策模拟与解释 | 输入游戏、场景、国家、币种、金额、设备、模拟器及可选用户偏好，查看逐步结果 |

模拟器必须展示：采用的配置版本、命中/未命中规则及原因、模板尝试链、每个方式的排除原因、最终顺序、推荐标签、默认选中结果、是否走兜底。模拟只做决策，不真实扣款。

### 8.1 新增关键配置字段

| 对象 | 建议字段 |
| --- | --- |
| 决策规则 | `rule_id`、作用域、`priority`、结构化条件、`template_id`、`effective_from/to`、状态 |
| 场景模板关联 | `template_id`、是否默认、`fallback_order`、绑定的发布版本 |
| 模板 | `template_id`、币种、兼容范围、`sort_mode`、`default_selection_policy`、发布版本 |
| 展示方式条目 | `display_method_key`、`sort_order`、`enabled`、推荐配置、候选执行路径；P1 再加置顶与有效期 |
| 执行路径 | PSP/商户账户/子渠道标识、能力约束、授权范围、状态；不在此文暴露商户密钥 |

能力元数据应有明确维护责任人。模板中的币种不能替代渠道实际支持币种，保存时与运行时都要检查。

### 8.2 发布治理

- 草稿 → 校验/模拟 → 复核 → 发布；生产规则与模板引用作为同一发布快照原子生效。
- 校验：默认/备用模板已发布且兼容、规则无同级冲突、展示 key 无重复、基础序号有效、至少有已配置可支付路径、推荐文案真实、活动有效期合理。
- 静态校验通过不保证实时可用，运行时仍需过滤和提交前复核。
- 模板下线、渠道禁用前展示影响范围和预计无支付方式的场景。普通发布不可静默清空兜底；紧急止损允许强制关闭，但须强提醒、记录和告警。
- 当前 Mock 中模板下线会更新场景关联；正式方案建议保留历史引用与失效原因，使用显式备用链处理，避免无法追溯。
- 支持按游戏/场景灰度、差异查看、审计、回滚；回滚配置不能恢复被安全紧急禁用的路径，也不改变已发起交易状态。

## 9. 例子与验收场景

以下方式名称和支持范围均为逻辑示例，不代表任何真实渠道在该地区/币种必然可用。

假设模板基础顺序：银行卡 → PayPal → 本地钱包；三者均在当前订单授权范围内。银行卡设推荐，用户最近成功使用 PayPal。

| 条件 | 最终结果 |
| --- | --- |
| P0 固定排序，三者可用 | 银行卡 → PayPal → 本地钱包；银行卡带推荐标签 |
| P1 偏好排序，无置顶 | PayPal → 银行卡 → 本地钱包；PayPal 可标“上次使用”，银行卡仍可带业务推荐标签 |
| P1 本地钱包有效置顶 | 本地钱包 → PayPal → 银行卡；是否默认选中另看选择策略 |
| 上例本地钱包禁用 | PayPal → 银行卡；置顶不突破禁用 |
| PayPal 维护，维护展示开启 | 可支付区按规则排序，PayPal 在底部置灰且不可选 |
| 用户本次已选银行卡 | 保留银行卡选择，不被偏好排序覆盖 |
| 同条件规则优先级 10 与 20 均命中 | 先尝试 10；其模板兼容但无可支付方式时再尝试 20 |
| 两条同优先级规则范围重叠 | 阻止发布，指出冲突条件 |
| USD 订单仅剩 CNY 默认模板 | 不使用该模板，继续检查显式兼容备用；没有则明确不可支付并告警 |
| 最高优先模板全不可用，备用模板可用 | 使用备用模板，输出完整兜底原因；不混合两个模板 |
| 缺少必要的付款国家 | 要求补充并重算；不将 IP 国家当作已验证交易国家 |
| 配置服务异常，有有效历史快照 | 仅在预先批准的作用域和有效期内使用最近成功发布快照，叠加当前安全校验；没有可靠校验来源则停止发起 |
| 已提交后超时，未确认失败 | 原尝试查单，不自动切换支付渠道 |
| 页面停留期间渠道被紧急关闭 | 提交前拦截；取消失效选择并提示，已受理交易继续查单 |
| 用户显式偏好 PayPal，银行卡运营置顶 | 偏好模式下 PayPal 在银行卡之前；不自动发起支付 |
| 上例 PayPal 不可用 | 跳过 PayPal，银行卡按置顶规则出现；保留但不消费不可用偏好 |
| 用户成功历史只有 1 笔 | 可作为最近成功信号，不能达到成功习惯模式最低证据；不足时按最近成功回退 |
| 偏好与运营置顶指向同一项 | 只展示一次，按最高优先层记录原因 |
| 无用户历史，但群体评分有效 | 数据模式可对未锁定项使用群体排序；不伪造“上次使用”标签 |
| 数据评分时本地钱包分数高于用户显式偏好 | 不越过显式偏好；只在剩余区调整 |
| 一个剩余候选无可信分数 | 未知候选保留原槽位，只重排可信项槽位；覆盖不足则剩余区整体回退 |
| 评分超时且偏好正常 | 偏好模式兜底；记录超时，不阻塞收银台展示 |
| 切换账户或撤回个性化授权 | 不读取旧账户/旧授权的历史；当前已发起支付仍独立处理 |
| 评分更新但用户正在填写银行卡信息 | 本会话不重排，不覆盖选择；下次决策使用新评分版本 |

## 10. 数据指标与迭代

### 10.1 主指标与口径

主指标建议为“收银台订单支付完成率”：进入收银台的去重有效订单中，在预先约定观察窗内完成支付的订单比例。按订单归因，不把一次订单的多次重试当成新增转化。

辅助指标：

- 可支付覆盖率、零可用方式率、模板兜底率、规则冲突率。
- 首次尝试成功率、最终完成率、完成耗时、用户切换方式比例、取消比例。
- 单方式曝光/选择/发起/成功漏斗；明确曝光为真实可见，不只记录服务端返回。
- 实际支付成本率、退款/拒付/投诉、重复扣款、超时未知状态率。
- 决策延迟与错误率，按游戏、地区、币种、设备、策略版本拆分。

必须区分：方式排序关注端到端支付完成；渠道健康关注已发起交易中的技术/处理结果。原始方式成功率会受到人群、排序位置及用户选择偏差影响，不能直接作为排序分数。

### 10.2 最小追踪信息

决策记录：`decision_id`、收银台会话 ID、订单 ID、策略/模板版本、命中规则、模板尝试链、初始和最终顺序、排除/兜底原因、推荐与默认选择结果；偏好/数据模式补充偏好快照引用、锁定层、模型/统计版本、特征快照引用、候选集、展示位置、分数、分群回退层级、数据截止时间及实验分组概率。

事件：`cashier_view`、`method_impression`、`method_select`、`payment_attempt`、`payment_result`；关联 `decision_id`、订单和支付尝试。客户端交互埋点与服务端最终结果分开，最终成功不能仅信客户端返回。

原因码示例：`RULE_MATCHED`、`SCENARIO_DEFAULT`、`TEMPLATE_EMPTY`、`CURRENCY_UNSUPPORTED`、`AMOUNT_OUT_OF_RANGE`、`DEVICE_UNSUPPORTED`、`METHOD_DISABLED`、`CHANNEL_UNAVAILABLE`、`EXPLICIT_PREFERENCE`、`LAST_SUCCESS_BOOST`、`FREQUENT_SUCCESS_BOOST`、`DATA_SCORE`、`INSUFFICIENT_EVIDENCE`、`SCORE_TIMEOUT`、`BASE_ORDER`。

不在日志保存完整卡号、支付令牌或不必要的个人信息；明确访问权限与保留周期。

### 10.3 分期范围

| 阶段 | 交付范围 | 暂不做 |
| --- | --- | --- |
| P0 可控上线 | 固定排序、统一硬过滤、确定性模板规则、兼容兜底、独立标签与选择策略、决策解释、版本/回滚、基础埋点 | 用户画像、自动成功率排名、自动跨渠道重试 |
| P1 偏好与稳定性 | 最近成功方式、限时置顶、偏好解释/清除/作用域；后续增加显式偏好与成功习惯；多路径可用性与健康熔断、灰度实验 | 黑盒综合分与无条件重试 |
| P2 数据优化 | 先 D1 分群统计排序，再评估 D2 上下文模型、D3 列表优化；保护偏好、处理冷启动和位置偏差，建立实验/降级闭环 | 用原始成功率简单降序、只追求低费率、无审批自动探索 |

动态策略先以影子模式记录建议，再做小范围随机对照实验。实验分组在会话内稳定，以订单级指标评估，预设样本量、观察窗和回滚阈值，不预先承诺收益。

## 11. 评审时必须确认的业务决策

1. 首期覆盖自建 Web、原生中的哪些场景；平台 IAP 与外部支付边界由谁审核。
2. 各方式的真实币种/国家/金额/设备/交易类型能力，以及商户账户授权数据来源。
3. 哪些同名 subchannel 可以合并成一个展示入口，哪些必须保留差异。
4. 默认选中是否采用“不预选”；如需预选，哪些场景满足明确确认与授权要求。
5. 普通维护是否隐藏；是否有必须保留置灰说明的市场或方式。
6. 配置发布、紧急停用、回滚的责任人，以及生产权限和复核制度。
7. 偏好作用域和授权/清除机制、历史有效窗口、是否提供显式偏好入口；首版是否只采用最近成功模式。
8. 数据排序的可用流量与埋点质量、观察窗和位置去偏方案、实验/成本预算及回滚门槛；是否具备受控探索的审批条件。

推荐首期评审结论：沿用模板基础顺序，先落地统一可用性过滤、确定性模板匹配、同币种兼容兜底和决策解释；用户偏好与动态排序在数据和安全闭环建立后再上线。

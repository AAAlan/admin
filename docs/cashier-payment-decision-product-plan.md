# 收银台支付方式排序产品方案

版本：V1.10 产品评审稿 · 2026-10-29

一句话说明：让用户优先看到当前能用、自己常用、容易完成付款的支付方式，同时让运营能够控制、预览和调整展示结果。

本文说明产品体验和业务规则，供产品、运营、支付团队评审；评分公式、数据口径和开发字段单独放在[技术附录](</Users/happyelements/Documents/cashier-admin 2/docs/cashier-payment-decision-technical-notes.md>)。本文为需求建议，不代表功能已上线。

## 一、我们要解决什么问题

目前已有支付方式添加、拖拽排序、推荐文案和场景关联能力。继续扩展时，需要解决三个问题：

1. 所有用户看到相同顺序，老用户还要反复寻找自己常用的方式。
2. 运营配置排在前面的方式，未必适合用户当前的地区、币种或设备。
3. 方式越来越多后，仅靠人工排序，难以持续判断怎样更容易完成支付。

本方案的目标是：减少用户找支付方式的时间，提高付款完成率；同时保留运营对展示范围、基础顺序和异常处理的控制。

适用范围为国内、海外的自建网页和原生收银台。平台内购是否允许第三方支付，先按平台政策及商户授权判断，不通过排序功能改变这些限制。本方案不负责自动换币，也不负责在支付状态不明时自动换渠道扣款。

## 二、用户会经历什么

一次收银台展示按以下顺序处理：

1. 确认适用范围。根据游戏、支付场景、订单币种、地区和设备，选择一套适用的收银台配置。
2. 确认哪些方式能用。排除不支持当前订单、设备不兼容、已关闭或不可支付的方式。
3. 排列展示顺序。按该场景选择的排序模式，决定用户先看到什么。
4. 展示辅助信息。按配置显示“推荐”“上次使用”等标签，并决定是否预先选中某一项。
5. 用户确认付款。用户自行选择并确认支付；发起前再次检查该方式是否仍可使用。

用户已经开始选择或填写付款信息后，不因普通配置或数据更新突然改变列表。只有订单条件变化、主动刷新或方式失效等情况，才重新判断，并保留仍然有效的用户选择。

每笔订单从“模板候选、逐方式及逐渠道判断”到“固定 / 偏好 / 数据排序、最终展示和用户确认”的完整流程，见[支付方式适用性 PRD 第 3.4 节：每笔订单的收银台支付方式决策流程](</Users/happyelements/Documents/cashier-admin 2/docs/cashier-payment-availability-prd.md#34-每笔订单的收银台支付方式决策流程>)。本单可支付集合先确定，任何排序模式都不能重新加入已被限制的方式。

## 三、提供哪三种排序方式

每个场景只采用一种排序模式。针对同一笔订单，三种模式共用相同的可用性判断规则，区别在于如何排列，不改变用户是否有资格使用某种方式。同一模板用于不同商品或订单时，可用支付方式可以不同。

| 排序模式 | 适用场景 | 用户看到的结果 |
| --- | --- | --- |
| 固定排序 | 新场景、方式较少、需要统一展示的场景 | 按运营设定的顺序展示 |
| 用户偏好排序 | 有重复付款行为，希望减少选择成本的场景 | 根据成功支付历史，优先展示用户熟悉的方式 |
| 数据驱动排序 | 方式较多、交易数据充分、需要持续优化的场景 | 优先展示根据成功历史判断的常用方式，再根据同类交易表现调整其余方式 |

### 3.1 固定排序：运营决定基础顺序

运营通过拖拽设置顺序。同一场景下，用户按这套顺序查看可用方式；其中某项不能使用时，将其移除，后面的方式自然前移。

例如，基础顺序为“银行卡、PayPal、本地钱包”。如果银行卡在当前订单不可用，则展示“PayPal、本地钱包”。

固定排序不根据个人支付历史调整位置，适合作为所有场景的基础方案和异常情况下的备用方案。

### 3.2 用户偏好排序：让用户更快找到熟悉的方式

用户不需要额外操作，系统根据已经成功完成的支付，判断其可能更愿意使用的方式，不增加偏好设置入口。

建议按以下顺序展示，根据成功历史最多提前一项，剩余方式保持基础顺序，同一方式只展示一次：

根据成功历史优先展示的方式 → 其余基础顺序。

没有有效成功记录时，不提前任何方式，直接使用基础顺序。

历史偏好提供两种选择：

- 上次成功使用：默认方案。优先展示近期曾成功使用、且本次仍可用的方式；最近的一项不可用时，可继续参考更早但仍有效的成功记录。
- 近期经常使用：后续扩展。优先展示近期多次成功使用的方式，并降低较早记录的影响；记录不足时回到“上次成功使用”。

初始建议参考最近 90 天内的记录，最终期限由业务和隐私评审确定。点击过、调起过、支付取消或银行拒绝，不直接代表用户喜欢或不喜欢。

使用边界：

- 默认不跨游戏、交易市场和币种复用历史；需要复用时另行确认范围。
- 游客、无授权或无有效历史时，跳过个人偏好，不影响正常支付。
- 根据历史判断的方式不可用时暂时跳过，不改写原有成功记录。
- 本次点击或选中不用于更新历史偏好，只有支付成功后才更新参考记录。
- 退出或切换账户后，不继续使用上一个账户的历史。

### 3.3 数据驱动排序：用交易效果优化剩余位置

在用户没有有效支付历史，或仍有多项方式需要排列时，系统参考同类场景的交易表现，将更可能帮助用户完成付款的方式适当前移。

判断时重点看两件事：用户是否愿意选择它，以及选择后是否容易支付成功。同时关注付款耗时和操作负担，不只看点击量，也不只看渠道成功率。

建议保留以下优先关系：

根据成功历史优先展示的方式 → 其余方式按交易效果排列。

数据优化默认保留历史偏好方式的位置，只调整其余方式。没有有效成功记录时，可对全部可用方式按交易效果排列；剩余方式不足两项时，不再调整。

特殊情况按以下规则处理：

- 新用户：可以参考同场景用户的整体表现，不虚构个人偏好。
- 新支付方式：先沿用运营基础顺序，不因没有数据就排在最后；验证可用后，再给予小范围展示机会。
- 数据少或效果接近：不频繁改动，保留已批准的顺序。
- 数据服务异常：回到用户偏好排序；个人历史也不可用时，使用运营基础方案。
- 某项缺少可信数据：保留该项原位置，只调整有充分依据的其它位置；整体依据不足时不调整。

成本是优化时需要考虑的条件，但不能为了低费率牺牲明显的支付体验，也不能偷偷隐藏用户本来可用的方式。数据排序是否有效，最终看订单付款完成情况，而不是某个内部评分。

### 3.4 用同一个例子理解三种模式

假设三种方式本次均可用，基础顺序为“银行卡、PayPal、本地钱包”；用户上次成功使用 PayPal。

| 模式 | 展示结果 | 为什么 |
| --- | --- | --- |
| 固定排序 | 银行卡、PayPal、本地钱包 | 完全沿用运营基础顺序 |
| 用户偏好排序 | PayPal、银行卡、本地钱包 | 上次成功使用的方式提前 |
| 数据驱动排序 | PayPal、本地钱包、银行卡 | 保留 PayPal；假设经验证本地钱包在同类场景更有利于完成付款，则将其提前 |

示例仅说明规则，不代表这些方式在任何地区都可用，也不代表某方式天然优于另一方式。

## 四、运营需要配置什么

沿用现有“全局模板”和“支付场景”入口，避免相同规则在多个地方重复维护。

### 4.1 收银台模板：配置展示内容

模板回答“有哪些方式，以及没有其它影响时按什么顺序展示”。

运营可以添加或关闭支付方式、调整基础顺序、配置推荐文案、设置默认选中规则，并选择模板默认使用的排序模式。相同支付方式经多个渠道接入时，原则上只向用户展示一个入口；有不同授权或交互要求时，不能仅凭名称相同就合并。

### 4.2 支付场景：配置适用范围

场景回答“什么情况下使用哪套模板”。

运营配置适用地区、币种、设备等条件，以及规则优先级、默认模板和备用模板。需要覆盖模板默认排序模式时，必须明确显示覆盖关系；没有覆盖则沿用模板设置。

多个条件同时命中时，按运营明确设置的优先级选择。相同优先级的规则如果可能同时生效，发布前必须提示冲突并要求调整，不能靠列表先后决定。

### 4.3 预览与发布：先看清影响，再生效

运营输入地区、币种、设备和用户历史示例后，应能看到实际展示结果，并理解：

- 使用了哪套模板，是否启用了备用模板。
- 哪些方式没有展示，原因是什么。
- 每一项为什么在这个位置，带什么标签，是否默认选中。
- 本次修改会影响哪些游戏和场景。

配置按“保存草稿、预览校验、复核、发布”生效。支持查看修改前后差异、分批生效和恢复上一版本。关闭模板或渠道前，提示受影响场景；紧急停用保留快速处理入口和操作记录。

### 4.4 单笔订单决策工作台

在“收银台支付方式决策”Demo 中，参考 Stripe 对启用、可用条件与动态展示的职责区分，以及 Adyen 的方式列表和详情侧栏，收敛为三个工作区：

- 支付方式：列表搜索及筛选，点击方式在侧栏维护启停和业务金额限制。机构能力、商户授权及渠道限额只读，不与业务规则混编。
- 展示策略：以排序模式、基础顺序为主；标签、默认选择和兼容备用模板按需展开，不重复维护支付方式。
- 测试预览：先看订单条件与收银台效果，再按需查看方式原因、执行过程和版本。多商品对比是测试子视图；评分、查询、原笔和渠道故障归入高级测试。

配置统一经过“查看变更并应用”，核对前后差异、典型商品数量影响及全部校验结果，再一起应用并进入测试。任何配置错误都阻止整体应用；草稿不影响当前预览，应用不恢复模拟故障。Demo 的本地版本切换不等同于生产审批发布。

用户手动选择后，普通历史及评分更新不打断展示；金额、资格、模板、规则或渠道状态变化仍立即重判。选择失效或模板切换时取消并说明，不自动替换。默认选择只在首次打开时应用，Demo 用“应用到 Demo 并测试”重开预览模拟；成功历史只来自本地虚构样本，更早历史标“曾成功使用”，不误称“上次成功”。

详细功能与逐项验收见[决策 PRD 第 3.5、7.3 节](</Users/happyelements/Documents/cashier-admin 2/docs/cashier-payment-availability-prd.md>)。本工作台只验证决策产品逻辑，不实现真实评分、机构、存储或支付服务。

## 五、所有模式都要遵守哪些规则

### 5.1 先保证能用，再讨论排位

模板配置候选范围，不保证每笔订单都展示全部方式。根据商品支付属性、本次含税及优惠后的实际支付金额、币种、商户能力和服务状态判断；标价满足但实付不满足时，不能放行。同一方式有多个渠道时，至少一条完整支持本单且已授权、启用、确认可用，才可作为可支付项参与排序。

详细商品规则、后台交互、金额边界、多渠道判断与验收见[支付方式适用规则 PRD](</Users/happyelements/Documents/cashier-admin 2/docs/cashier-payment-availability-prd.md>)。配套 Demo 独立使用示例数据，不代表真实支付或发布能力已经上线。

不满足平台政策、商户授权、地区、币种、金额或设备要求的方式，不展示。已经禁用的方式，也不能因为用户常用而重新出现。

区分“可用、本单不适用、待满足条件、暂时不可用、未能确认”。本单不适用默认隐藏；可补条件时提供操作；相关维护或查询异常项置灰说明，不参与可支付排序、选中或推荐。正常填卡及支付认证不算不可用。查询失败不能解释为商品不支持，保留独立确认可用的其他方式。

查询绑定当前订单、商户和规则版本，过期或旧订单结果不能放行；发起前再次校验。草稿、生效版本和渠道即时状态分开，错误草稿不影响已生效方式。

排序功能只决定展示；用户确认之后由哪个支付渠道处理，是另一项支付能力，不能通过调整展示顺序偷偷改变授权要求。

### 5.2 备用模板不能放宽支付条件

按“命中条件的模板、场景默认模板、已配置的备用模板”的顺序尝试。同一层有多个候选时，使用运营已设定的优先顺序。

每套模板都必须适合当前订单。某套模板没有可用方式时，继续尝试下一套；选定后不混入其它模板的方式。

不能从另一个游戏、另一订单币种或不兼容的支付环境中寻找替代。全部不可用时，明确提示用户并通知运营处理，不返回一个看似可支付的列表。

### 5.3 排序、推荐和默认选中分别配置

| 产品能力 | 含义 | 不代表什么 |
| --- | --- | --- |
| 展示排序 | 用户先看到哪一项 | 不代表该项一定推荐 |
| 推荐标签 | 展示“推荐”等说明 | 不自动改变顺序 |
| 默认选中 | 进入时是否预先选择或展开某项 | 不代表用户已授权或已付款 |

默认建议不预选。按场景需要，也可选择“第一项”或“优先上次成功方式”；后者无有效记录时回到第一可用项。用户自行选择后，以本次选择为准。

推荐文案必须对当前订单真实成立。“商户成本低”不能宣传为“用户手续费低”；“上次使用”只在确有成功记录时出现。现有多推荐项配置可兼容，但建议一个场景只设置一个主推方式。

### 5.4 支付异常要让用户知道下一步

| 情况 | 用户体验与处理 |
| --- | --- |
| 用户取消支付 | 返回收银台，保留选择，不自动重试 |
| 发起前方式变为不可用 | 提示重新选择，取消失效选择，不悄悄切换另一方式 |
| 已确认支付失败 | 说明原因；用户确认后可以换方式再试 |
| 支付处理中、超时或结果未知 | 显示查询状态，继续确认原笔结果，不自动另扣一笔 |
| 没有可用方式 | 明确提示暂无可用方式，提供重试或帮助入口，并向运营告警 |
| 排序或历史服务异常 | 使用基础展示方案；仍需通过支付资格与安全检查 |

支付已被受理后，配置变更或紧急停用不影响原笔订单继续查结果、接收回调和对账。配置恢复也不能重新开放因安全原因紧急关闭的方式。

## 六、怎么上线，怎么判断有用

### 6.1 分三期推进

| 阶段 | 交付重点 | 达成什么结果 |
| --- | --- | --- |
| 第一期：可控展示 | 固定排序、可用性判断、模板匹配与备用、预览解释、发布与恢复 | 用户不看到错误方式；运营能解释和控制结果 |
| 第二期：减少选择 | 先支持上次成功方式，再扩展近期经常使用 | 老用户更快找到熟悉的方式 |
| 第三期：持续优化 | 先按同场景交易表现排序，验证后再考虑更复杂的模型 | 在保护既有体验的前提下，提高订单付款完成率 |

### 6.2 核心成功指标：更多订单完成付款

核心指标为“收银台订单付款完成率”：发起收银台的有效订单中，在约定时间内完成付款的订单占比。

同一订单多次进入、换方式或重试，只算一笔订单。主动离开、没有可用方式、页面或决策加载失败的订单仍保留，不能通过少展示、少统计来提高结果。付款结果以支付系统最终确认为准。

建议将数据驱动排序的首轮业务目标设为：相对用户偏好排序，订单付款完成率相对提升至少 1%。例如从 80% 提升到 80.8%，是相对提升 1%，不是提升 1 个百分点。

目前没有真实业务基线。以下数字仅作为评审起点，不代表现状或收益承诺；实验前需结合流量、历史表现和样本量冻结正式目标。

### 6.3 三种模式分别怎样才算成功

| 排序模式 | 重点验证 | 建议成功标准 |
| --- | --- | --- |
| 固定排序 | 展示正确、配置可控 | 因本功能配置错误而展示不适用方式或造成无方式可用的订单为 0；付款完成率相比原方案不明显下降 |
| 用户偏好排序 | 老用户更快找到熟悉方式 | 对有有效历史的用户，确认支付方式的中位耗时降低至少 10%；整单付款完成率不明显下降，未发起付款的比例不恶化 |
| 数据驱动排序 | 在偏好方案基础上带来额外完成 | 相比用户偏好排序，整单付款完成率相对提升至少 1%，结果通过事先约定的实验检验，且不突破安全、体验和成本限制 |

“不明显下降”不能只看两组数值接近或没有统计结论，而是上线前约定可接受的最大损失，并有足够样本证明没有超过它。偏好排序的体验目标在有历史用户中评估，但整体及无历史用户的付款表现也要检查。

### 6.4 辅助指标：解释为什么变好或变差

| 指标 | 业务含义 | 期望方向 |
| --- | --- | --- |
| 支付方式确认耗时 | 从方式列表可操作，到用户首次主动选择或确认某方式所花时间；自动预选不算确认 | 降低，同时观察较慢用户的体验 |
| 支付发起率 | 发起收银台的订单中，有多少真正发起了付款 | 不下降或提高，避免只让少数用户更快 |
| 首次尝试成功率 | 已发起付款的订单中，第一笔尝试就成功的占比 | 结合整单完成率观察，不作为单独放量依据 |
| 支付方式切换率 | 用户主动选择两种及以上方式的订单占比 | 减少不必要切换，但不以限制选择来降低 |
| 历史方式使用率 | 有有效历史的订单中，首次尝试使用了历史优先方式的占比 | 用于判断历史参考是否有帮助，不越高越好 |
| 完成付款耗时 | 从发起收银台到确认付款成功所花时间 | 缩短，同时检查未完成订单比例 |

这些指标用来解释结果，不能替代整单付款完成率。首位点击增加、内部评分升高、某渠道成功率提高，都不等于产品已经成功。

### 6.5 必须守住的底线

- 资金与合规：因本功能导致的重复扣款、未经用户确认发起支付、展示未授权或不适用方式，均为 0；出现确认事故立即停止新策略并处理原笔交易。
- 可支付与稳定性：无可用方式、列表加载失败、异常降级的比例不超过预先约定上限；列表响应不能超出约定等待时间。安全检查失败时不能为了维持展示而放行。
- 体验：用户选择不被覆盖，填写信息时列表不跳动；投诉及支付结果未知的情况不超过预设风险线。
- 成本与长期风险：单笔成功支付成本不超过批准预算，退款和拒付不明显恶化；观察期未结束时不把它们判为达标。

### 6.6 如何决定放量

固定与偏好、偏好与数据驱动分别做小范围对照。比较时保持页面、候选方式、推荐文案和默认选中策略一致，避免把其它改动的效果算给排序。实验前确定基线、目标、可接受损失、样本量、付款观察期和停止规则。

只有“本阶段目标达成、整体及关键人群表现可接受、所有底线通过、数据可信”同时满足，才逐步放量。样本不足或结果不明确时继续观察；达到最大实验期限仍不明确，则保持原方案。出现安全事故立即止损，其它指标超出风险线按预案回退，不因某一项提升而忽略整体损失。

退款、拒付等长期风险尚未完成观察时，仅维持批准范围内的小流量验证，不宣布全面达标或直接全量上线。

### 6.7 评审重点

本轮需确认：首期覆盖哪些支付场景、哪些场景需要默认选中，以及各市场的成功目标、可接受损失和观察期。

建议先把固定排序和异常处理做完整，再上线“上次成功使用”的偏好排序；数据驱动作为独立的后续优化能力评估。
